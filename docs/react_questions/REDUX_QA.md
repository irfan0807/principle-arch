## Q1: What is Redux and what problem does it solve?

**Answer:**

Redux is a predictable state container for JavaScript applications. It solves the problem of **shared mutable state** across components that don't have a direct parent-child relationship.

**Without Redux:**
```
ComponentA (has user data)
  └─ ComponentB
       └─ ComponentC
            └─ ComponentD (needs user data) ← prop drilling through B and C
```

**With Redux:**
```
Redux Store (single source of truth)
  ├── ComponentA reads via useSelector
  └── ComponentD reads via useSelector (no prop drilling)
```

**Three principles of Redux:**
1. **Single source of truth** — One store holds the entire application state tree.
2. **State is read-only** — The only way to change state is to dispatch an action.
3. **Changes via pure functions** — Reducers are pure functions: `(state, action) => newState`.

**In FoodDash**, Redux manages auth state (user, isAuthenticated, isLoading) and cart state (items, restaurantId, restaurantName) — state that's needed across many pages and must survive page refreshes.

## Q2: What is Redux Toolkit and why did FoodDash choose it over vanilla Redux?

**Answer:**

Redux Toolkit (RTK) is the official, opinionated toolset for efficient Redux development. It wraps Redux with sensible defaults and eliminates boilerplate.

**Vanilla Redux vs Redux Toolkit:**

| Aspect | Vanilla Redux | Redux Toolkit |
|--------|--------------|---------------|
| Action creators | Manual `const ADD_ITEM = "ADD_ITEM"` | Auto-generated by `createSlice` |
| Immutability | Manual spread: `{...state, count: state.count + 1}` | Immer: `state.count += 1` (mutative syntax, immutable under the hood) |
| Store setup | `createStore` + manual middleware | `configureStore` with defaults (thunk, dev tools, serializability check) |
| Async logic | Manual thunk middleware setup | `createAsyncThunk` built-in |
| Boilerplate | ~50 lines per feature | ~15 lines per feature |
| DevTools | Manual integration | Enabled by default |

**FoodDash chose RTK because:**
1. **70% less boilerplate** — `createSlice` generates action creators and action types automatically.
2. **Immer integration** — Write mutative code that produces immutable updates (no spread operator chains).
3. **Built-in thunks** — `createAsyncThunk` for `fetchUser` and `signOutUser` API calls.
4. **DevTools by default** — `configureStore` enables Redux DevTools automatically.
5. **TypeScript-first** — Excellent type inference from `createSlice`.

## Q3: Explain the FoodDash Redux store structure. How is it configured?

**Answer:**

```typescript
// store/store.ts
import { configureStore, combineReducers } from "@reduxjs/toolkit";
import { persistStore, persistReducer } from "redux-persist";
import storage from "redux-persist/lib/storage"; // localStorage

const cartPersistConfig = {
  key: "cart",
  storage,
};

const persistedCartReducer = persistReducer(cartPersistConfig, cartReducer);

export const store = configureStore({
  reducer: {
    cart: persistedCartReducer,
    auth: authReducer,
  },
  middleware: (getDefaultMiddleware) =>
    getDefaultMiddleware({
      serializableCheck: {
        ignoredActions: ["persist/PERSIST", "persist/REHYDRATE"],
      },
    }),
});

export const persistor = persistStore(store);

export type RootState = ReturnType<typeof store.getState>;
export type AppDispatch = typeof store.dispatch;
```

**Key decisions:**
1. **Only cart is persisted** — Auth state is fetched fresh on every app load via `fetchUser()` thunk. Persisting auth would risk stale tokens.
2. **Serializable check exception** — `redux-persist` dispatches non-serializable actions (`PERSIST`, `REHYDRATE`). Without the exception, Redux would warn on every page load.
3. **Type exports** — `RootState` and `AppDispatch` are exported for typed hooks (`useAppSelector`, `useAppDispatch`).

## Q4: How does the `cartSlice` work? Walk through every reducer.

**Answer:**

```typescript
// store/slices/cartSlice.ts
interface CartState {
  items: CartItem[];
  restaurantId: string | null;
  restaurantName: string | null;
}

const initialState: CartState = {
  items: [],
  restaurantId: null,
  restaurantName: null,
};

const cartSlice = createSlice({
  name: "cart",
  initialState,
  reducers: {
    addItem: (state, action: PayloadAction<{
      menuItem: MenuItem;
      restaurantId: string;
      restaurantName: string;
    }>) => {
      const { menuItem, restaurantId, restaurantName } = action.payload;

      // Restaurant guard: clear cart if switching restaurants
      if (state.restaurantId && state.restaurantId !== restaurantId) {
        state.items = [];
      }

      state.restaurantId = restaurantId;
      state.restaurantName = restaurantName;

      // Increment quantity if item already exists
      const existing = state.items.find(i => i.id === menuItem.id);
      if (existing) {
        existing.quantity += 1;
      } else {
        state.items.push({ ...menuItem, quantity: 1 });
      }
    },

    removeItem: (state, action: PayloadAction<string>) => {
      state.items = state.items.filter(i => i.id !== action.payload);
      if (state.items.length === 0) {
        state.restaurantId = null;
        state.restaurantName = null;
      }
    },

    updateQuantity: (state, action: PayloadAction<{
      itemId: string;
      quantity: number;
    }>) => {
      const item = state.items.find(i => i.id === action.payload.itemId);
      if (item) {
        item.quantity = Math.max(0, action.payload.quantity);
        if (item.quantity === 0) {
          state.items = state.items.filter(i => i.id !== action.payload.itemId);
        }
      }
      if (state.items.length === 0) {
        state.restaurantId = null;
        state.restaurantName = null;
      }
    },

    clearCart: (state) => {
      state.items = [];
      state.restaurantId = null;
      state.restaurantName = null;
    },
  },
});
```

**Business logic in reducers:**
1. **Single-restaurant constraint** — Adding items from a different restaurant clears the cart first (you can't order from two restaurants simultaneously).
2. **Quantity deduplication** — Adding the same item twice increments quantity instead of creating a duplicate entry.
3. **Auto-cleanup** — Removing the last item also clears `restaurantId` and `restaurantName`.
4. **Zero quantity removal** — Setting quantity to 0 removes the item entirely.

## Q5: How does the `authSlice` work with `createAsyncThunk`?

**Answer:**

```typescript
// store/slices/authSlice.ts

// Async thunk for fetching user
export const fetchUser = createAsyncThunk(
  "auth/fetchUser",
  async (_, { rejectWithValue }) => {
    try {
      const res = await fetch("/api/auth/user", { credentials: "include" });
      if (res.status === 401) return null; // Not authenticated
      if (!res.ok) throw new Error("Failed to fetch user");
      return await res.json();
    } catch (error) {
      return rejectWithValue(error.message);
    }
  }
);

// Async thunk for sign out
export const signOutUser = createAsyncThunk(
  "auth/signOutUser",
  async () => {
    await fetch("/api/auth/logout", {
      method: "POST",
      credentials: "include",
    });
  }
);

const authSlice = createSlice({
  name: "auth",
  initialState: {
    user: null as User | null,
    isLoading: true,   // Starts true — assume loading until fetchUser resolves
    isAuthenticated: false,
  },
  reducers: {},
  extraReducers: (builder) => {
    builder
      .addCase(fetchUser.pending, (state) => {
        state.isLoading = true;
      })
      .addCase(fetchUser.fulfilled, (state, action) => {
        state.user = action.payload;
        state.isAuthenticated = !!action.payload;
        state.isLoading = false;
      })
      .addCase(fetchUser.rejected, (state) => {
        state.user = null;
        state.isAuthenticated = false;
        state.isLoading = false;
      })
      .addCase(signOutUser.fulfilled, (state) => {
        state.user = null;
        state.isAuthenticated = false;
      });
  },
});
```

**Key design decisions:**
1. **`isLoading: true` by default** — Prevents flash of unauthenticated UI on page load. The `ProtectedRoute` shows a spinner until `fetchUser` resolves.
2. **401 returns `null`, not rejected** — A 401 is not an error; it means the user isn't logged in. Treating it as a rejection would trigger error handling.
3. **`extraReducers` vs `reducers`** — Thunk lifecycle actions (`pending`, `fulfilled`, `rejected`) are handled in `extraReducers` because they're auto-generated, not manually defined.
4. **No `reducers` defined** — Auth state is only modified through thunks (API calls). There's no local-only auth action.

## Q6: What are Redux selectors and why are memoized selectors important?

**Answer:**

Selectors are functions that extract specific pieces of state from the Redux store:

```typescript
// Simple selectors
export const selectCartItems = (state: RootState) => state.cart.items;
export const selectCartRestaurantId = (state: RootState) => state.cart.restaurantId;
export const selectUser = (state: RootState) => state.auth.user;
export const selectIsAuthenticated = (state: RootState) => state.auth.isAuthenticated;

// Derived/computed selector
export const selectCartTotal = (state: RootState) =>
  state.cart.items.reduce(
    (total, item) => total + parseFloat(item.price) * item.quantity,
    0
  );

export const selectCartItemCount = (state: RootState) =>
  state.cart.items.reduce((count, item) => count + item.quantity, 0);
```

**Why memoization matters:**

Without memoization, `selectCartTotal` runs on EVERY state change (even auth changes), creating a new number each time. For computed selectors that return objects or arrays, this causes unnecessary re-renders:

```typescript
// ❌ Returns new array reference every time — triggers re-render even if items didn't change
const selectExpensiveItems = (state: RootState) =>
  state.cart.items.filter(item => parseFloat(item.price) > 20);

// ✅ Memoized with reselect — same reference if input didn't change
import { createSelector } from "@reduxjs/toolkit";

const selectExpensiveItems = createSelector(
  [selectCartItems],
  (items) => items.filter(item => parseFloat(item.price) > 20)
);
```

**`createSelector` (reselect):**
- Caches the last result.
- Only recomputes when input selectors return new values.
- Included in Redux Toolkit by default.

## Q7: Why did FoodDash migrate from Zustand to Redux Toolkit for cart state?

**Answer:**

**Previous architecture (Zustand):**
```typescript
const useCartStore = create<CartStore>()(
  persist(
    (set, get) => ({
      items: [],
      addItem: (item) => set(state => ({ items: [...state.items, item] })),
      getTotal: () => get().items.reduce((sum, i) => sum + i.price * i.quantity, 0),
    }),
    { name: "cart-storage" }
  )
);
```

**Why migrate:**

| Factor | Zustand | Redux Toolkit |
|--------|---------|---------------|
| DevTools | Basic (via middleware) | Full time-travel debugging, action log, state diff |
| Persistence | Built-in `persist` middleware | `redux-persist` with more control (whitelist/blacklist, migrations) |
| Unified store | Separate from auth | Cart + auth in single store |
| Middleware | Custom only | Built-in thunks, serialization checks, custom middleware chain |
| Ecosystem | Small | Huge (RTK Query, reselect, redux-saga if needed) |
| Team familiarity | Newer library | Industry standard, easier to hire for |
| Testing | Direct store calls | Well-established patterns (dispatch action, assert state) |

**The trigger:** When auth moved to Redux (from Context), having cart in Zustand and auth in Redux created split-brain state management. For example, `clearCart` on sign-out required coordinating between two separate stores. Unifying into Redux eliminated this.

**When Zustand is still better:** Simple, isolated stores where DevTools aren't needed (e.g., UI toggle state, form state within a single page).

## Q8: What is Immer and how does Redux Toolkit use it internally?

**Answer:**

Immer allows you to write mutative code that produces immutable updates. Redux Toolkit wraps every `createSlice` reducer with Immer.

**Without Immer (vanilla Redux):**
```typescript
// Must manually spread at every level
case "UPDATE_ITEM_QUANTITY":
  return {
    ...state,
    items: state.items.map(item =>
      item.id === action.payload.id
        ? { ...item, quantity: action.payload.quantity }
        : item
    ),
  };
```

**With Immer (Redux Toolkit):**
```typescript
// Direct mutation syntax — Immer creates immutable update under the hood
updateQuantity: (state, action) => {
  const item = state.items.find(i => i.id === action.payload.itemId);
  if (item) {
    item.quantity = action.payload.quantity; // Looks like mutation, but isn't!
  }
}
```

**How Immer works internally:**
1. Creates a **draft** (Proxy-wrapped copy of state).
2. Your reducer mutates the draft.
3. Immer records all changes via Proxy traps.
4. Produces a new immutable state object with only the changed paths.

**Rules when using Immer in RTK:**
- Either mutate the draft OR return a new value — never both.
- Don't destructure `state` at the top level (breaks the Proxy).
- Primitives can't be mutated — `state = 5` doesn't work. Return the new value instead.

## Q9: What is `redux-persist` and how does FoodDash configure it?

**Answer:**

`redux-persist` automatically saves Redux state to a storage engine (localStorage, sessionStorage, AsyncStorage) and rehydrates it on app start.

**FoodDash configuration:**
```typescript
const cartPersistConfig = {
  key: "cart",           // localStorage key: "persist:cart"
  storage,               // defaults to localStorage
  // No whitelist/blacklist — persist entire cart slice
};

const persistedCartReducer = persistReducer(cartPersistConfig, cartReducer);
```

**App wrapper:**
```tsx
<Provider store={store}>
  <PersistGate loading={null} persistor={persistor}>
    {/* App renders only after rehydration */}
  </PersistGate>
</Provider>
```

**Why only cart is persisted:**
- **Cart** — Users expect their cart to survive page refreshes and browser restarts.
- **Auth** — NOT persisted. Fresh `fetchUser()` on every app load ensures the session is still valid. Persisting stale auth would show a logged-in UI when the session has expired.

**`PersistGate`** — Blocks rendering until rehydration is complete. Without it, the cart would flash "0 items" for a split second before showing the real count.

**Serialization exception:**
```typescript
middleware: (getDefaultMiddleware) =>
  getDefaultMiddleware({
    serializableCheck: {
      ignoredActions: ["persist/PERSIST", "persist/REHYDRATE"],
    },
  }),
```
`redux-persist` dispatches actions with non-serializable payloads (register, rehydrate). Without this exception, Redux throws warnings.

## Q11: What is `createAsyncThunk` and how does it handle the async lifecycle?

**Answer:**

`createAsyncThunk` generates three action types for an async operation:

```typescript
export const fetchUser = createAsyncThunk(
  "auth/fetchUser",  // action type prefix
  async (arg, thunkAPI) => {
    const res = await fetch("/api/auth/user", { credentials: "include" });
    return await res.json();
  }
);

// Auto-generated action types:
// "auth/fetchUser/pending"    — dispatched when thunk starts
// "auth/fetchUser/fulfilled"  — dispatched with return value on success
// "auth/fetchUser/rejected"   — dispatched with error on failure
```

**Lifecycle handling in `extraReducers`:**
```typescript
extraReducers: (builder) => {
  builder
    .addCase(fetchUser.pending, (state) => {
      state.isLoading = true;
      state.error = null;
    })
    .addCase(fetchUser.fulfilled, (state, action) => {
      state.isLoading = false;
      state.user = action.payload;
      state.isAuthenticated = !!action.payload;
    })
    .addCase(fetchUser.rejected, (state, action) => {
      state.isLoading = false;
      state.error = action.error.message;
      state.isAuthenticated = false;
    });
}
```

**`thunkAPI` provides:**
- `dispatch` — dispatch other actions inside the thunk.
- `getState` — read current Redux state.
- `rejectWithValue(value)` — return a typed rejection payload.
- `signal` — AbortController signal for cancellation.

**FoodDash uses thunks for:**
- `fetchUser` — GET `/api/auth/user` on app load.
- `signOutUser` — POST `/api/auth/logout` + clear state.

## Q12: What is the difference between `reducers` and `extraReducers` in `createSlice`?

**Answer:**

| Aspect | `reducers` | `extraReducers` |
|--------|-----------|----------------|
| Action creators | Auto-generated | External (from thunks, other slices) |
| Use case | Synchronous, local slice actions | Responding to async thunks or cross-slice actions |
| Action types | `sliceName/reducerName` | Custom string or thunk lifecycle types |
| Export | `slice.actions.actionName` | N/A — actions come from elsewhere |

**FoodDash examples:**

```typescript
// cartSlice uses `reducers` — all synchronous local actions
const cartSlice = createSlice({
  name: "cart",
  reducers: {
    addItem: (state, action) => { /* ... */ },
    removeItem: (state, action) => { /* ... */ },
    updateQuantity: (state, action) => { /* ... */ },
    clearCart: (state) => { /* ... */ },
  },
  // No extraReducers — cart doesn't react to async actions
});

// authSlice uses `extraReducers` — all async thunk responses
const authSlice = createSlice({
  name: "auth",
  reducers: {},  // No synchronous actions
  extraReducers: (builder) => {
    builder
      .addCase(fetchUser.pending, ...)
      .addCase(fetchUser.fulfilled, ...)
      .addCase(fetchUser.rejected, ...)
      .addCase(signOutUser.fulfilled, ...);
  },
});
```

**Cross-slice communication via `extraReducers`:**
```typescript
// If cart should clear on signout:
const cartSlice = createSlice({
  name: "cart",
  reducers: { /* ... */ },
  extraReducers: (builder) => {
    builder.addCase(signOutUser.fulfilled, (state) => {
      state.items = [];
      state.restaurantId = null;
      state.restaurantName = null;
    });
  },
});
```

## Q13: How do typed hooks (`useAppSelector`, `useAppDispatch`) work and why are they critical?

**Answer:**

```typescript
// store/hooks.ts
import { TypedUseSelectorHook, useDispatch, useSelector } from "react-redux";
import type { RootState, AppDispatch } from "./store";

export const useAppDispatch: () => AppDispatch = useDispatch;
export const useAppSelector: TypedUseSelectorHook<RootState> = useSelector;
```

**Why critical for FoodDash:**

1. **Selector type safety:**
```typescript
// ✅ Typed — TypeScript knows `items` is CartItem[]
const items = useAppSelector(state => state.cart.items);

// ✅ Catches errors — 'cart.itms' would be a compile error
const items = useAppSelector(state => state.cart.itms); // TS Error!

// ❌ Untyped useSelector — returns `any`, no error catching
const items = useSelector(state => state.cart.itms); // No error :(
```

2. **Dispatch type safety:**
```typescript
// ✅ Typed — knows fetchUser() returns a thunk
const dispatch = useAppDispatch();
dispatch(fetchUser()); // Works with async thunks

// ❌ Untyped useDispatch — doesn't accept thunks
const dispatch = useDispatch();
dispatch(fetchUser()); // TS Error: thunk is not an Action
```

3. **Refactoring safety:** Rename `state.cart.items` to `state.cart.cartItems` → TypeScript flags every component that accesses the old path.

## Q14: What is the Redux middleware chain? How does it work in FoodDash?

**Answer:**

Middleware sits between dispatching an action and the reducer processing it. Each middleware can inspect, modify, delay, or stop actions.

```
dispatch(action)
    │
    ▼
[Thunk Middleware] — Intercepts functions, calls them with (dispatch, getState)
    │
    ▼
[Serializable Check] — Warns if action/state contains non-serializable values
    │
    ▼
[redux-persist] — Handles PERSIST/REHYDRATE actions, saves state to storage
    │
    ▼
[Redux DevTools] — Records action for time-travel debugging
    │
    ▼
[Reducer] — Processes action, produces new state
```

**FoodDash middleware config:**
```typescript
configureStore({
  middleware: (getDefaultMiddleware) =>
    getDefaultMiddleware({
      serializableCheck: {
        ignoredActions: ["persist/PERSIST", "persist/REHYDRATE"],
      },
    }),
  // Default middleware includes: thunk + serializableCheck + immutabilityCheck
});
```

**Custom middleware example — cart analytics:**
```typescript
const cartAnalyticsMiddleware: Middleware = (store) => (next) => (action) => {
  if (action.type === "cart/addItem") {
    analytics.track("item_added_to_cart", {
      itemId: action.payload.menuItem.id,
      restaurantId: action.payload.restaurantId,
    });
  }
  return next(action); // Always call next to continue the chain
};
```

## Q15: What is the difference between Redux and React Context for state management?

**Answer:**

| Feature | Redux | React Context |
|---------|-------|--------------|
| Re-render behavior | Selector-based — only subscribed components re-render | ALL consumers re-render when ANY value changes |
| DevTools | Full time-travel, action log, state diff | None (invisible in devtools) |
| Persistence | `redux-persist` ecosystem | Manual localStorage logic |
| Middleware | Thunks, sagas, custom middleware chain | None — use `useEffect` for side effects |
| Performance | Optimized with `reselect` memoization | No built-in optimization — requires `useMemo` workarounds |
| Async | `createAsyncThunk` | Manual promise handling |
| Boilerplate | Moderate (RTK reduces it significantly) | Minimal |
| Testing | Dispatch action → assert state | Render with Provider → assert output |

**Why FoodDash migrated auth FROM Context TO Redux:**

```typescript
// Context problem: updating user.lastLogin re-renders EVERY consumer
const AuthContext = createContext({ user, isLoading, isAuthenticated, signOut });
// Components reading only `isAuthenticated` still re-render when `user` changes

// Redux solution: components subscribe to exactly what they need
const isAuthenticated = useAppSelector(selectIsAuthenticated);
// Only re-renders when isAuthenticated changes, NOT when user.lastLogin changes
```

**Context is still used for:** ThemeProvider — simple, rarely changes, no DevTools needed.

## Q16: What is Redux Saga and how does it compare to Redux Thunk?

**Answer:**

| Aspect | Redux Thunk | Redux Saga |
|--------|------------|------------|
| Complexity | Simple — functions with dispatch/getState | Complex — ES6 generators with effects |
| Learning curve | Low | High |
| Testing | Mock fetch, dispatch | Pure effect assertions (no mocking) |
| Cancellation | Manual AbortController | Built-in `takeLatest`, `cancel` |
| Complex workflows | Nested async/await | Powerful: race, fork, join, channel |
| Bundle size | ~1KB | ~25KB |
| FoodDash usage | ✅ Used for `fetchUser`, `signOutUser` | ❌ Not used (thunks are sufficient) |

**When Saga would be useful for FoodDash:**
```typescript
// Complex order workflow with race condition handling
function* watchOrderPlacement() {
  while (true) {
    const action = yield take("ORDER_PLACED");
    const { timeout, response } = yield race({
      response: call(api.createOrder, action.payload),
      timeout: delay(30000), // 30 second timeout
    });
    if (timeout) {
      yield put(orderTimedOut());
    } else {
      yield put(orderConfirmed(response));
    }
  }
}
```

**Why FoodDash uses thunks:** The async needs are simple (fetch user, sign out). No complex orchestration, race conditions, or cancellation patterns that would justify Saga's complexity.

## Q17: How does the Redux DevTools extension help debug FoodDash?

**Answer:**

Redux DevTools provides:

1. **Action Log:**
```
cart/addItem          → {menuItem: {id: "pizza-1", name: "Margherita"}, restaurantId: "r1"}
cart/addItem          → {menuItem: {id: "pasta-2", name: "Carbonara"}, restaurantId: "r1"}
cart/updateQuantity   → {itemId: "pizza-1", quantity: 3}
auth/fetchUser/pending
auth/fetchUser/fulfilled → {id: "user-1", name: "John", role: "customer"}
```

2. **State Diff:** Shows exactly which keys changed per action:
```diff
  cart:
    items:
-     [0].quantity: 1
+     [0].quantity: 3
```

3. **Time-Travel Debugging:** Click any past action to see the state at that point. Skip/replay actions to reproduce bugs.

4. **State Snapshot:** Export/import state JSON for bug reports.

## Q20: How does `redux-persist` handle state migrations when the schema changes?

**Answer:**

When you change the persisted state shape (add/remove/rename fields), old persisted data in localStorage may be incompatible. `redux-persist` supports migrations:

```typescript
const migrations = {
  // Version 1 → 2: Added restaurantName field
  1: (state: any) => ({
    ...state,
    restaurantName: null,
  }),
  // Version 2 → 3: Renamed price to unitPrice
  2: (state: any) => ({
    ...state,
    items: state.items.map((item: any) => ({
      ...item,
      unitPrice: item.price,
    })),
  }),
};

const cartPersistConfig = {
  key: "cart",
  storage,
  version: 3,
  migrate: createMigrate(migrations, { debug: false }),
};
```

**How it works:**
1. `redux-persist` stores a `_persist.version` number alongside the state.
2. On rehydration, if stored version (e.g., 1) < config version (e.g., 3), it runs migrations 1→2, then 2→3.
3. Each migration receives the previous state and returns the transformed state.

**FoodDash consideration:** Currently no migrations are configured (version defaults to -1). If the cart state shape changes in a future release, migrations would prevent existing users from losing their cart contents.

## Q22: How does state normalization work and why does it matter?

**Answer:**

**Denormalized (nested) state:**
```typescript
{
  orders: [
    {
      id: "o1",
      restaurant: { id: "r1", name: "Bella Italia", rating: 4.5 },
      items: [
        { id: "i1", name: "Margherita", price: 12.99 },

      items: [{ id: "i1", name: "Margherita", price: 12.99 }],     // DUPLICATED!
    },
  ]
}
```

**Normalized state:**
```typescript
{
  orders: {
    ids: ["o1", "o2"],
    entities: {
      o1: { id: "o1", restaurantId: "r1", itemIds: ["i1", "i2"] },
      o2: { id: "o2", restaurantId: "r1", itemIds: ["i1"] },

    },
  },
}
```

1. **No duplication** — Restaurant "Bella Italia" stored once. Rating update applies everywhere.
2. **O(1) lookups** — `entities["r1"]` vs scanning an array.
3. **Simpler updates** — Update one entity without touching arrays.
4. **Consistent data** — No risk of "Bella Italia" having rating 4.5 in one order and 4.3 in another.

## Q23: What are Redux action types and naming conventions?

**Answer:**

**Action type format:** `domain/eventDescription`

```typescript

"cart/addItem"
"cart/removeItem"
"cart/updateQuantity"
"cart/clearCart"

// Thunk lifecycle (auto-generated):
```

**Naming conventions:**

## Q25: What is RTK Query and how does it compare to React Query?

**Answer:**

RTK Query is Redux Toolkit's data fetching/caching solution, built into the Redux store.

| Feature | RTK Query | React Query (TanStack Query) |
|---------|-----------|------------------------------|
| State location | Inside Redux store | Separate cache (outside Redux) |
| DevTools | Redux DevTools | React Query DevTools |

| Optimistic updates | `onQueryStarted` + patch | `onMutate` + manual cache update |

| Bundle size | Included with RTK | Separate package (~12KB) |
| Server-side rendering | Good support | Excellent support |

**Why FoodDash chose React Query over RTK Query:**
1. **Separation of concerns** — Server state (API data) is fundamentally different from client state (cart, auth). Mixing them in one Redux store creates confusion.
2. **Team familiarity** — React Query was already in use before the Redux migration.
3. **Simpler mental model** — Query keys are intuitive (`["/api/restaurants"]`). RTK Query's tag-based invalidation has a steeper learning curve.
4. **Independence** — React Query works without Redux. If the team later removes Redux, React Query continues working unchanged.

## Q26: How does state immutability work in Redux? Why is it important?

**Answer:**

**Immutability means:** Never modify existing state directly. Always create a new state object.

**Why it matters:**
1. **Change detection** — Redux uses `===` reference comparison. If you mutate the existing object, `oldState === newState` is `true`, and React won't re-render.
2. **Time-travel debugging** — DevTools stores references to past states. Mutation would corrupt history.
3. **Predictability** — Pure reducers with immutable updates guarantee that the same action + state always produces the same result.

**Common mutation bugs:**
```typescript
// ❌ MUTATION — sorts the existing array in place
state.items.sort((a, b) => a.price - b.price);

// ✅ IMMUTABLE — creates a new sorted array
const sorted = [...state.items].sort((a, b) => a.price - b.price);
return { ...state, items: sorted };

// ✅ WITH IMMER (RTK) — Immer handles immutability
state.items.sort((a, b) => a.price - b.price); // Safe inside createSlice!
```

**Immer's role in RTK:** You can write mutative code inside `createSlice` reducers because Immer converts it to immutable updates. Outside `createSlice`, you must maintain immutability manually.

## Q27: What is the flux architecture and how does Redux implement it?

**Answer:**

**Flux pattern:**
```
Action → Dispatcher → Store → View → Action → ...
```

**Redux implementation:**
```
dispatch(action) → Middleware → Reducer → New State → useSelector → Re-render
```

| Flux Concept | Redux Equivalent |
|-------------|-----------------|
| Action | Plain object `{ type, payload }` |
| Dispatcher | `store.dispatch()` |
| Store | Single store (Flux allowed multiple) |
| View | React components with `useSelector` |

**Key Redux deviations from Flux:**
1. **Single store** — Flux had multiple stores. Redux has one store with multiple slices.
2. **Pure reducers** — Flux stores had mutation. Redux reducers are pure functions.
3. **Middleware** — Redux added the middleware concept for side effects (thunks, sagas).
4. **Unidirectional flow** — Both enforce one-way data flow: View → Action → Store → View.

## Q28: How does `useSelector` cause re-renders and how do you optimize them?

**Answer:**

`useSelector` subscribes to the Redux store. On every dispatch, it runs the selector function and compares the result with the previous result using `===`.

**Re-render problem:**
```typescript
// ❌ Returns new object every time — ALWAYS re-renders
const { items, total } = useAppSelector(state => ({
  items: state.cart.items,
  total: state.cart.items.reduce((sum, i) => sum + i.price * i.quantity, 0),
}));
// {} !== {} even if contents are identical
```

**Solutions:**

1. **Multiple `useSelector` calls:**
```typescript
// ✅ Primitive values — only re-renders when value actually changes
const items = useAppSelector(state => state.cart.items);
const restaurantId = useAppSelector(state => state.cart.restaurantId);
```

2. **`shallowEqual` comparison:**
```typescript
import { shallowEqual } from "react-redux";

const { items, restaurantId } = useAppSelector(
  state => ({ items: state.cart.items, restaurantId: state.cart.restaurantId }),
  shallowEqual  // Compares each property instead of the object reference
);
```

3. **Memoized selectors with `createSelector`:**
```typescript
const selectCartSummary = createSelector(
  [selectCartItems],
  (items) => ({
    count: items.length,
    total: items.reduce((sum, i) => sum + parseFloat(i.price) * i.quantity, 0),
  })
);
// Only recomputes when items array reference changes
```

## Q29: What is the `PersistGate` component and why is it necessary?

**Answer:**

```tsx
<PersistGate loading={null} persistor={persistor}>
  <App />
</PersistGate>
```

**What it does:**
1. On app start, `redux-persist` asynchronously reads state from localStorage.
2. `PersistGate` blocks rendering of children until rehydration completes.
3. During rehydration, it renders the `loading` prop (or `null`).
4. After rehydration, it renders children with the full persisted state.

**Why it's necessary for FoodDash:**

Without `PersistGate`:

```

Frame 2: Rehydration complete → Cart shows 3 items immediately
// No flash
```

## Q30: How would you implement undo/redo functionality with Redux?

**Answer:**

Redux's immutable state model makes undo/redo straightforward because every state is a snapshot:

```typescript
interface UndoableState<T> {
  past: T[];
  present: T;
  future: T[];
}

function undoable<T>(reducer: Reducer<T>): Reducer<UndoableState<T>> {
  const initialState: UndoableState<T> = {
    past: [],
    present: reducer(undefined, { type: "@@INIT" }),
    future: [],
  };

  return (state = initialState, action) => {
    switch (action.type) {
      case "UNDO": {
        const previous = state.past[state.past.length - 1];
        return {
          past: state.past.slice(0, -1),
          present: previous,
          future: [state.present, ...state.future],
        };
      }
      case "REDO": {
        const next = state.future[0];
        return {
          past: [...state.past, state.present],
          present: next,
          future: state.future.slice(1),
        };
      }
      default: {
        const newPresent = reducer(state.present, action);
        if (newPresent === state.present) return state; // No change
        return {
          past: [...state.past, state.present],
          present: newPresent,
          future: [], // Clear future on new action
        };
      }
    }
  };
}
```

**FoodDash use case:** Undo "clear cart" — user accidentally clears cart, clicks "Undo" within 5 seconds to restore it. The `past` array holds the previous cart state.

## Q35: How do you handle loading and error states in Redux?

**Answer:**

**Pattern: Enum state machine:**
```typescript
type RequestStatus = "idle" | "loading" | "succeeded" | "failed";

interface AuthState {
  user: User | null;
  status: RequestStatus;
  error: string | null;
}

const authSlice = createSlice({
  name: "auth",
  initialState: {
    user: null,
    status: "idle" as RequestStatus,
    error: null as string | null,
  },
  extraReducers: (builder) => {
    builder
      .addCase(fetchUser.pending, (state) => {
        state.status = "loading";
        state.error = null;
      })
      .addCase(fetchUser.fulfilled, (state, action) => {
        state.status = "succeeded";
        state.user = action.payload;
      })
      .addCase(fetchUser.rejected, (state, action) => {
        state.status = "failed";
        state.error = action.error.message ?? "Unknown error";
      });
  },
});
```

**Why enum > boolean flags:**
```typescript
// ❌ Boolean flags — impossible states possible
{ isLoading: true, isError: true }  // Loading AND error at the same time?!

// ✅ Enum — only one state at a time
status: "loading"  // Can't be "failed" simultaneously
```

**Component usage:**

```typescript
function AuthStatus() {

  if (status === "loading") return <Spinner />;
  if (status === "failed") return <Alert variant="destructive">{error}</Alert>;
  return <UserProfile />;
```

## Q36: What is the `dispatch` function and what can you dispatch?

**Answer:**

`dispatch` sends actions to the Redux store. With RTK's default middleware, you can dispatch:

1. **Plain action objects:**
```typescript
dispatch({ type: "cart/clearCart" });
dispatch(clearCart()); // Same thing via action creator
```

2. **Async thunks (functions):**
```typescript
dispatch(fetchUser()); // Thunk middleware intercepts, calls the function
```

3. **Batch of actions (with thunk):**
```typescript
dispatch((dispatch, getState) => {
  dispatch(clearCart());
  dispatch(signOutUser());
});
```

**What you cannot dispatch:**
- Promises (use `createAsyncThunk` instead)
- Non-serializable values in payload (Dates, functions, class instances)
- Actions without a `type` property

**Dispatch is synchronous for plain actions:**
```typescript
dispatch(addItem(item));
console.log(store.getState().cart); // Already updated!

// But thunks are async:
await dispatch(fetchUser()); // Wait for API call
console.log(store.getState().auth); // Now updated
```

## Q37: How does React Query complement Redux in FoodDash? What's the boundary?

**Answer:**

**Clear boundary:**

| Data Type | Technology | Reason |
|-----------|-----------|--------|
| User authentication state | Redux (authSlice) | Client-owned, needed everywhere, must be synchronous |
| Shopping cart | Redux (cartSlice) | Client-owned, persisted, needs DevTools |
| Restaurant list | React Query | Server-owned, cacheable, background refetch |
| Menu items | React Query | Server-owned, changes rarely |
| Order history | React Query | Server-owned, paginated |
| Order tracking (real-time) | React Query + WebSocket | Server-owned, real-time updates |

**How they interact:**

```typescript
// React Query fetches server data
const { data: restaurants } = useQuery({ queryKey: ["/api/restaurants"] });

// Redux manages client state
const cartItems = useAppSelector(selectCartItems);

// Mutation bridges both
const createOrder = useMutation({
  mutationFn: (data) => apiRequest("POST", "/api/orders", data),
  onSuccess: () => {
    dispatch(clearCart());                                    // Redux action
    queryClient.invalidateQueries({ queryKey: ["/api/orders"] }); // React Query invalidation
  },
});
```

**Rule:** If the server is the source of truth → React Query. If the client is the source of truth → Redux.

## Q38: What are Redux action patterns for optimistic updates?

**Answer:**

```typescript
// Approach 1: Optimistic reducer + rollback action
const cartSlice = createSlice({
  name: "cart",
  reducers: {
    addItemOptimistic: (state, action) => {
      state.items.push(action.payload);
    },
    rollbackAddItem: (state, action) => {
      state.items = state.items.filter(i => i.tempId !== action.payload.tempId);
    },
  },
});

// Usage
const tempItem = { ...item, tempId: uuid() };
dispatch(addItemOptimistic(tempItem));
try {
  await api.addItem(item);
} catch {
  dispatch(rollbackAddItem(tempItem));
}
```

```typescript
// Approach 2: createAsyncThunk with manual cache update
export const addItemToServer = createAsyncThunk(
  "cart/addItemToServer",
  async (item, { dispatch, rejectWithValue }) => {
    dispatch(addItemOptimistic(item)); // Optimistic update
    try {
      return await api.addItem(item);
    } catch (error) {
      dispatch(rollbackAddItem(item)); // Rollback on failure
      return rejectWithValue(error.message);
    }
  }
);
```

**FoodDash approach:** Since the cart is client-side only (not synced to server), optimistic updates aren't needed for cart. They ARE used with React Query's `onMutate` for server mutations (order status updates).

## Q39: What is `getDefaultMiddleware` and what does it include?

**Answer:**

```typescript
configureStore({
  middleware: (getDefaultMiddleware) =>
    getDefaultMiddleware({
      serializableCheck: { ignoredActions: ["persist/PERSIST"] },
    }),
});
```

**Default middleware includes:**

1. **`redux-thunk`** — Allows dispatching functions for async logic.
2. **Serializable state invariant middleware** (dev only) — Warns if non-serializable values exist in state or actions (Dates, Maps, Sets, functions).
3. **Immutable state invariant middleware** (dev only) — Warns if state is mutated outside reducers.

**Why these defaults:**
- **Thunk** — Most common async pattern. Included so you don't need to install it separately.
- **Serializable check** — Redux state must be serializable for DevTools (time-travel), persistence (localStorage), and SSR (hydration).
- **Immutable check** — Catches accidental mutations that would break Redux's change detection.

**Extending with custom middleware:**
```typescript
middleware: (getDefaultMiddleware) =>
  getDefaultMiddleware().concat(analyticsMiddleware, sentryMiddleware),
```

## Q41: What is `rejectWithValue` in `createAsyncThunk`?

**Answer:**

`rejectWithValue` lets you return a typed rejection payload instead of a generic error:

```typescript
export const fetchUser = createAsyncThunk(
  "auth/fetchUser",
  async (_, { rejectWithValue }) => {
    try {
      const res = await fetch("/api/auth/user", { credentials: "include" });
      if (res.status === 401) return null;
      if (!res.ok) {
        const errorData = await res.json();
        return rejectWithValue(errorData); // Typed rejection payload
      }
      return await res.json();
    } catch (error) {
      return rejectWithValue({ message: "Network error", code: "NETWORK" });
    }
  }
);

// In extraReducers:
.addCase(fetchUser.rejected, (state, action) => {
  if (action.payload) {
    // rejectWithValue payload — typed and structured
    state.error = action.payload.message; // "Network error"
    state.errorCode = action.payload.code; // "NETWORK"
  } else {
    // Unhandled throw — generic error
    state.error = action.error.message;
  }
})
```

**Without `rejectWithValue`:** A thrown error produces `action.error` with `name`, `message`, `stack` — but you can't add custom fields (HTTP status, error code, validation details).

**With `rejectWithValue`:** `action.payload` contains exactly what you passed — structured, typed, and useful for displaying specific error messages to users.

## Q42: How do you handle cross-slice dependencies in Redux?

**Answer:**

**Problem:** Cart should clear when user signs out, but `signOutUser` is in `authSlice`.

**Solution 1: `extraReducers` (recommended):**
```typescript
// cartSlice listens to auth actions
const cartSlice = createSlice({
  name: "cart",
  reducers: { /* ... */ },
  extraReducers: (builder) => {
    builder.addCase(signOutUser.fulfilled, (state) => {
      // Clear cart when user signs out
      state.items = [];
      state.restaurantId = null;
      state.restaurantName = null;
    });
  },
});
```

**Solution 2: Thunk coordination:**
```typescript
export const signOutAndClearCart = createAsyncThunk(
  "auth/signOutAndClearCart",
  async (_, { dispatch }) => {
    await dispatch(signOutUser());
    dispatch(clearCart());
  }
);
```

**Solution 3: Middleware:**
```typescript
const signOutMiddleware: Middleware = (store) => (next) => (action) => {
  const result = next(action);
  if (action.type === "auth/signOutUser/fulfilled") {
    store.dispatch(clearCart());
  }
  return result;
};
```

**FoodDash uses Solution 1** — `extraReducers` keeps the dependency explicit and testable. Each slice declares what external actions it responds to.

## Q43: What are the common anti-patterns in Redux?

**Answer:**

**1. Storing derived state:**
```typescript
// ❌ Storing computed value — becomes stale
state.cartTotal = state.items.reduce(...);

// ✅ Compute on the fly with selector
const selectCartTotal = createSelector(
  [selectCartItems],
  (items) => items.reduce((sum, i) => sum + i.price * i.quantity, 0)
);
```

**2. Putting everything in Redux:**
```typescript
// ❌ Form input state in Redux — excessive re-renders and boilerplate
dispatch(setEmailInput("user@example.com"));

// ✅ Local state for ephemeral values
const [email, setEmail] = useState("");
```

**3. Giant reducers:**
```typescript
// ❌ One reducer handling 50 action types
function appReducer(state, action) {
  switch (action.type) { /* 500 lines */ }
}

// ✅ Split into domain slices
configureStore({ reducer: { cart, auth, orders, notifications } });
```

**4. Mutating state outside Immer:**
```typescript
// ❌ Mutation outside createSlice
const items = useAppSelector(selectCartItems);
items.push(newItem); // Mutates Redux state directly!

// ✅ Always dispatch
dispatch(addItem(newItem));
```

**5. Non-serializable state:**
```typescript
// ❌ Storing class instances, functions, Dates
dispatch(setUser(new User({ ... }))); // Class instance
dispatch(setCreatedAt(new Date()));    // Date object

// ✅ Store plain objects and strings
dispatch(setUser({ id: "1", name: "John" }));
dispatch(setCreatedAt(new Date().toISOString()));
```

## Q44: What is the `connect` HOC and why has `useSelector`/`useDispatch` replaced it?

**Answer:**

`connect` is the legacy HOC for connecting class components to Redux:

```typescript
// Old pattern with connect
class CartPage extends Component {
  render() {
    return <div>Items: {this.props.items.length}</div>;
  }
}

const mapStateToProps = (state) => ({
  items: state.cart.items,
  total: selectCartTotal(state),
});

const mapDispatchToProps = { addItem, removeItem, clearCart };

export default connect(mapStateToProps, mapDispatchToProps)(CartPage);
```

**Why hooks replaced it:**

| Aspect | `connect` HOC | `useSelector`/`useDispatch` |
|--------|-------------|---------------------------|
| Boilerplate | `mapStateToProps`, `mapDispatchToProps`, `connect()` | Direct selector/dispatch calls |
| TypeScript | Complex generic types | Natural inference |
| Testing | Must unwrap HOC or mock connect | Test component directly |
| DevTools | Extra wrapper in component tree | Clean component tree |
| Readability | Props are injected implicitly | Data sources are explicit |
| Composition | Wrapper hell with multiple HOCs | Linear hook composition |

**FoodDash uses hooks exclusively.** The only remaining `connect` use case is class components (e.g., Error Boundaries), but even those can access Redux via render props or a wrapper functional component.

## Q45: How do you handle pagination with Redux?

**Answer:**

```typescript
interface OrdersState {
  items: Order[];
  page: number;
  pageSize: number;
  totalCount: number;
  hasMore: boolean;
  status: "idle" | "loading" | "succeeded" | "failed";
}

export const fetchOrders = createAsyncThunk(
  "orders/fetchOrders",
  async ({ page, pageSize }: { page: number; pageSize: number }) => {
    const res = await fetch(`/api/orders?page=${page}&limit=${pageSize}`);
    return await res.json(); // { data: Order[], total: number }
  }
);

const ordersSlice = createSlice({
  name: "orders",
  initialState: {
    items: [],
    page: 1,
    pageSize: 20,
    totalCount: 0,
    hasMore: true,
    status: "idle",
  } as OrdersState,
  reducers: {},
  extraReducers: (builder) => {
    builder.addCase(fetchOrders.fulfilled, (state, action) => {
      state.items = action.meta.arg.page === 1
        ? action.payload.data          // Replace on first page
        : [...state.items, ...action.payload.data]; // Append on subsequent pages
      state.totalCount = action.payload.total;
      state.page = action.meta.arg.page;
      state.hasMore = state.items.length < action.payload.total;
      state.status = "succeeded";
    });
  },
});
```

**FoodDash uses React Query for pagination instead** (since order data is server-owned):
```typescript
const { data, fetchNextPage, hasNextPage } = useInfiniteQuery({
  queryKey: ["/api/orders"],
  getNextPageParam: (lastPage) => lastPage.nextCursor,
});
```

## Q47: How does Redux handle concurrent dispatches? Is it thread-safe?

**Answer:**

JavaScript is single-threaded, so Redux is inherently "thread-safe" — there's no true concurrency. However, there are ordering concerns:

**Synchronous dispatches are sequential:**
```typescript
dispatch(addItem(itemA)); // Reducer runs immediately, state updated
dispatch(addItem(itemB)); // Runs after itemA is in state
// State is deterministic
```

**Async thunks can interleave:**
```typescript
dispatch(fetchUser());   // Starts API call 1
dispatch(fetchOrders()); // Starts API call 2 while call 1 is pending

// API call 2 might resolve before call 1
// Both resolved states are applied correctly because
// each reducer handles its own slice independently
```

**Race condition risk:**
```typescript
// ❌ Two rapid addItem dispatches with the same item
dispatch(addItem(pizza)); // quantity = 1
dispatch(addItem(pizza)); // quantity = 2 (correct — reducers are synchronous)

// ✅ No race condition because dispatch is synchronous
// Each reducer runs to completion before the next dispatch
```

**Where concurrency matters:** Async thunks that read state and then dispatch:
```typescript
dispatch(async (dispatch, getState) => {
  const items = getState().cart.items;  // Read state
  // ... API call takes 2 seconds ...
  // Another dispatch might have changed cart.items during those 2 seconds!
  dispatch(processItems(items)); // Potentially stale items!
});
```
**Fix:** Read state AFTER the async operation, or use `getState()` at the point of use.

## Q48: What is the `createAction` utility in Redux Toolkit?

**Answer:**

`createAction` creates typed action creators with optional payload preparation:

```typescript
import { createAction } from "@reduxjs/toolkit";

// Simple action
const clearCart = createAction("cart/clearCart");
clearCart(); // { type: "cart/clearCart" }

// Action with typed payload
const addItem = createAction<{ id: string; name: string; price: number }>("cart/addItem");
addItem({ id: "p1", name: "Margherita", price: 12.99 });
// { type: "cart/addItem", payload: { id: "p1", name: "Margherita", price: 12.99 } }

// Action with prepare callback
const addItemWithTimestamp = createAction("cart/addItem", (item: MenuItem) => ({
  payload: {
    ...item,
    addedAt: Date.now(),
    tempId: crypto.randomUUID(),
  },
}));
```

**When to use standalone `createAction`:**
- Actions shared across multiple slices.
- Actions dispatched from middleware.
- When you need the `prepare` callback for complex payload transformation.

**In FoodDash:** `createSlice` generates action creators automatically, so standalone `createAction` is rarely needed. It's mainly used for shared actions that multiple slices respond to via `extraReducers`.

## Q49: How do you implement feature flags with Redux?

```typescript
interface FeatureFlagsState {

export const fetchFeatureFlags = createAsyncThunk(
```

## Q50: What are the best practices for Redux in a production application like FoodDash?

**Answer:**

**1. Use Redux Toolkit — never vanilla Redux:**
```typescript
// ✅ createSlice, configureStore, createAsyncThunk
// ❌ switch-case reducers, manual action types, createStore
```

**2. Keep state minimal:**
```typescript
// ✅ Store IDs, compute derived data in selectors
state.cart.items // [{id, quantity, price}]
selectCartTotal(state) // computed

// ❌ Store computed values
state.cart.total // gets stale
```

**3. Use selectors everywhere:**
```typescript
// ✅ Abstracted — can change state shape without touching components
const items = useAppSelector(selectCartItems);

// ❌ Direct access — breaks if you rename state.cart.items
const items = useAppSelector(state => state.cart.items);
```

**4. Type everything:**
```typescript
// ✅ Typed hooks, typed PayloadAction, typed selectors
useAppSelector, useAppDispatch, PayloadAction<T>

// ❌ Untyped useSelector, `any` payloads
```

**5. Colocate slice + selectors + thunks:**
```
cartSlice.ts contains: createSlice + selectors + thunks
// Not spread across 3 files
```

**6. Only persist what's needed:**
```typescript
// ✅ Persist cart (user expectation)
// ❌ Persist loading states, error messages, or server data
```

**7. Test reducers as pure functions:**
```typescript
const result = cartReducer(initialState, addItem(payload));
expect(result.items).toHaveLength(1);
// No React rendering needed
```

**8. Use `createSelector` for derived data:**
```typescript
// ✅ Memoized — doesn't recompute unless items change
const selectCartTotal = createSelector([selectCartItems], items => ...);

// ❌ Recomputes on every render
const total = useAppSelector(state =>
  state.cart.items.reduce(...)
);
```

**9. Handle all async states:** `idle → loading → succeeded | failed`

**10. Document slice boundaries:** Each slice owns a domain. Cross-slice communication uses `extraReducers`, never direct imports of another slice's state.
