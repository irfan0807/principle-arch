# Scalability & Availability — 50 Interview Q&A for Senior Fullstack Engineers

---

## 1. What is scalability and why does it matter?

Scalability is a system's ability to handle growing workloads by adding resources without degrading performance. There are two types: **vertical scaling** (adding more CPU/RAM to a single machine) and **horizontal scaling** (adding more machines behind a load balancer). For a senior engineer, scalability matters because business growth is unpredictable — a system that can't scale will hit bottlenecks in CPU, memory, database connections, or network I/O. Good scalable design uses stateless services, partitioned databases, async processing, and caching layers. You measure scalability by throughput (requests/sec), latency percentiles (p50, p95, p99), and resource utilization under load. A well-scaled system maintains consistent response times whether serving 100 or 10 million users. The key principle is to identify the bottleneck (Amdahl's Law) and scale that specific component. Real-world scalability also involves cost efficiency — you want linear or sub-linear cost growth relative to traffic. Always design for 10x your current load, and have a plan for 100x.

---

## 2. What is the difference between vertical and horizontal scaling?

**Vertical scaling (scale-up)** means upgrading a single server's hardware — more CPU cores, RAM, faster SSDs, or better network cards. It's simpler (no code changes needed), but has hard limits (you can't add infinite RAM to one box) and creates a single point of failure. **Horizontal scaling (scale-out)** means adding more identical servers behind a load balancer to distribute traffic. It's theoretically unlimited and provides redundancy, but requires stateless application design, distributed data management, and more complex deployment. Vertical scaling suits databases that are hard to distribute (e.g., a single PostgreSQL primary). Horizontal scaling suits stateless API servers, microservices, and read replicas. Most production systems use **both**: vertically scale the database to the largest practical instance, then horizontally scale with read replicas and application-tier load balancing. The industry trend favors horizontal scaling because cloud platforms make it easy to spin up/down instances. Cost-wise, vertical scaling has diminishing returns — a 2x bigger instance often costs 3-4x more. Horizontal scaling with commodity hardware is typically more cost-effective at scale.

## 3. How does a load balancer work and what algorithms does it use?

A load balancer distributes incoming network traffic across multiple backend servers to ensure no single server is overwhelmed. It sits between clients and servers, accepting connections and forwarding them based on an algorithm. **Round Robin** sends requests sequentially to each server — simple but ignores server load. **Weighted Round Robin** assigns more traffic to more powerful servers. **Least Connections** routes to the server with the fewest active connections — best for long-lived connections like WebSockets. **IP Hash** hashes the client IP to always route to the same server — useful for session affinity but hurts distribution. **Layer 4 (TCP)** load balancers route based on IP/port without inspecting content — very fast (e.g., AWS NLB). **Layer 7 (HTTP)** load balancers inspect headers, URLs, and cookies to make smarter routing decisions (e.g., AWS ALB, Nginx). Health checks continuously ping backend servers and remove unhealthy ones from the pool. Modern load balancers also handle SSL termination, compression, and rate limiting. For global distribution, **DNS-based load balancing** (Route 53, Cloudflare) routes users to the nearest data center. In Kubernetes, services like Envoy or Istio provide service mesh-level load balancing with circuit breaking and retries.

## 4. What is high availability and how do you measure it?

High availability (HA) means a system remains operational and accessible for a very high percentage of time, minimizing downtime. It's measured in "nines": **99.9% (three nines)** allows ~8.7 hours/year downtime, **99.99% (four nines)** allows ~52 minutes/year, and **99.999% (five nines)** allows ~5.2 minutes/year. HA is achieved through **redundancy** (no single points of failure), **failover mechanisms** (automatic switching to standby systems), and **fault tolerance** (continued operation despite component failures). Key metrics include **MTBF** (Mean Time Between Failures) — how often failures happen, and **MTTR** (Mean Time To Recovery) — how fast you recover. Availability = MTBF / (MTBF + MTTR). To improve HA: deploy across multiple availability zones, use database replication with automatic failover, implement health checks and auto-healing, and design for graceful degradation. A critical concept is that **overall system availability is the product of all component availabilities** — if your app server is 99.99% and your database is 99.99%, the system is 99.98%. This is why reducing dependencies and having fallbacks for each component is essential.

## 5. Explain the CAP theorem and its practical implications.

The **CAP theorem** (Brewer's theorem) states that a distributed system can guarantee at most **two** of three properties: **Consistency** (every read receives the most recent write), **Availability** (every request receives a non-error response), and **Partition tolerance** (the system works despite network splits between nodes). Since network partitions are inevitable in distributed systems, you're really choosing between **CP** (consistent but may reject requests during partitions — e.g., HBase, MongoDB with majority writes) and **AP** (available but may return stale data during partitions — e.g., Cassandra, DynamoDB). In practice, this is a **spectrum, not a binary choice**. Systems like DynamoDB let you choose per-query: strong consistency (CP) or eventual consistency (AP). Most modern architectures use **eventual consistency** for non-critical data (product catalogs, social feeds) and **strong consistency** for critical data (payments, inventory). The PACELC theorem extends CAP: even when there's **no partition**, you still trade off between **latency** and **consistency**. For senior engineers, the key takeaway is: understand your data's consistency requirements per use case, don't apply one model everywhere, and design compensating mechanisms (conflict resolution, CRDTs) for eventually consistent data.

## 6. What is database sharding and when should you use it?

Database sharding is a horizontal partitioning strategy where data is distributed across multiple independent database instances (shards), each holding a subset of the total data. You choose a **shard key** (e.g., user_id, tenant_id, region) and a **sharding function** (hash-based, range-based, or directory-based) to determine which shard stores each record. **Hash-based sharding** (user_id % N) distributes evenly but makes range queries hard. **Range-based sharding** (users A-M on shard 1, N-Z on shard 2) supports range queries but can create hotspots. **Directory-based sharding** uses a lookup table for flexible mapping but adds a single point of failure. You should shard when: a single database can't handle the write throughput, data exceeds single-server storage, or you need to isolate tenants for compliance. **Downsides are significant**: cross-shard queries require scatter-gather, joins across shards are extremely expensive, maintaining referential integrity is complex, and rebalancing shards when adding nodes is operationally painful. Before sharding, exhaust simpler options: read replicas, connection pooling, query optimization, caching, and vertical scaling. Tools like Vitess (MySQL), Citus (PostgreSQL), or built-in sharding in MongoDB can help manage the complexity.

## 7. How do you design a system to handle 1 million concurrent users?

First, do the math: 1M concurrent users at 1 request/sec = 1M RPS, but typical browsing might be 0.1 req/sec = 100K RPS. Use a **CDN** (CloudFront, Cloudflare) to serve static assets (images, JS, CSS) — this offloads 60-80% of requests. Place a **global load balancer** (DNS-based) routing users to the nearest region, with regional ALBs distributing across **auto-scaling groups** of stateless application servers. Each app server should handle ~1-5K concurrent connections (Node.js/Go excel here). Use **Redis/Memcached** for session storage and hot data caching to reduce database load by 90%+. The database layer needs **read replicas** (5-10 replicas) for read-heavy workloads, with writes going to a primary. For write-heavy patterns, use **message queues** (Kafka, SQS) to buffer and process asynchronously. Implement **connection pooling** (PgBouncer) to handle thousands of app-to-DB connections. Use **database partitioning/sharding** if single-primary writes become a bottleneck. Monitor with distributed tracing (Jaeger), metrics (Prometheus/Grafana), and alerting. Key architecture: Client → CDN → Global LB → Regional LB → Auto-scaling App Servers → Cache Layer → Database (Primary + Replicas) → Async Queue Workers.

## 8. What is a CDN and how does it improve scalability?

A **Content Delivery Network (CDN)** is a geographically distributed network of edge servers that cache and serve content close to end users. When a user in Tokyo requests an image, instead of fetching it from your origin server in Virginia, the CDN serves it from an edge node in Tokyo — reducing latency from ~200ms to ~20ms. CDNs handle **static content** (images, CSS, JS, fonts, videos) and increasingly **dynamic content** through edge computing. Popular CDNs include CloudFront (AWS), Cloudflare, Akamai, and Fastly. For scalability, CDNs offload **60-90% of total traffic** from your origin servers, dramatically reducing bandwidth costs and server load. CDNs also provide **DDoS protection** by absorbing attack traffic across their massive global infrastructure. Cache invalidation strategies include **TTL-based expiry** (set Cache-Control headers), **versioned URLs** (app.v2.js), and **purge APIs** for immediate invalidation. Advanced CDN features include edge functions (Cloudflare Workers, Lambda@Edge) for running logic at the edge, A/B testing, header manipulation, and geo-routing. The key configuration is setting proper cache headers: `Cache-Control: public, max-age=31536000, immutable` for versioned assets, and shorter TTLs for dynamic content.

## 9. Explain the difference between stateful and stateless architectures.

A **stateless** architecture means each request contains all information needed to process it — the server doesn't store client session data between requests. A **stateful** architecture means the server maintains client state (sessions, connections, caches) across requests. Stateless is critical for horizontal scaling: any server can handle any request, so you simply add more servers behind a load balancer. If a stateless server dies, requests seamlessly route to another server. Stateful servers require **sticky sessions** (route the same client to the same server), which creates uneven load distribution and complicates failover. To make applications stateless: store sessions in **external stores** (Redis, DynamoDB), use **JWTs** for authentication (token carries the state), and put shared state in **distributed caches** or databases. However, some services are inherently stateful: **WebSocket connections**, **database connections**, **in-memory caches**, and **stream processing**. For these, use patterns like consistent hashing for routing, graceful connection draining during deploys, and state replication. The 12-Factor App methodology mandates stateless processes as a core principle. In Kubernetes, stateless apps use **Deployments** while stateful apps use **StatefulSets** with persistent volumes.

## 10. How does database replication work and what are the consistency models?

Database replication copies data from a **primary (master)** to one or more **replicas (slaves)** for read scaling, high availability, and disaster recovery. **Synchronous replication** waits for replicas to confirm writes before responding to the client — guarantees consistency but adds latency (used in financial systems). **Asynchronous replication** responds to the client immediately and replicates in the background — faster but replicas may lag (replication lag can be milliseconds to seconds). **Semi-synchronous** waits for at least one replica to acknowledge. **Single-leader replication** (PostgreSQL, MySQL) routes all writes to one primary and reads to replicas — simple but the primary is a write bottleneck. **Multi-leader replication** (CockroachDB, DynamoDB Global Tables) allows writes on multiple nodes, enabling multi-region writes but requiring conflict resolution. **Leaderless replication** (Cassandra, Riak) uses quorum reads/writes — write to W nodes, read from R nodes, where W + R > N ensures consistency. Common consistency issues: **read-your-writes** (user writes then reads stale data from replica) — solve by routing reads-after-writes to primary. **Monotonic reads** (user sees newer then older data) — solve with session-based replica affinity. Always monitor replication lag and alert if it exceeds your tolerance.

## 11. What is caching and what strategies do you use at different layers?

Caching stores frequently accessed data in faster storage to reduce latency and backend load. **Browser cache**: HTTP headers (Cache-Control, ETag) tell browsers to cache static assets locally. **CDN cache**: Edge servers cache content geographically close to users. **Application cache**: In-process caches (Node.js Map, Guava) for hot data — fastest but not shared across instances. **Distributed cache**: Redis or Memcached shared across all app servers — ideal for sessions, API responses, computed results. **Database cache**: Query result caches and buffer pools within the DB engine. **Cache strategies**: **Cache-aside (Lazy Loading)** — app checks cache, on miss fetches from DB and populates cache; good for read-heavy, but first request is always slow. **Write-through** — writes go to cache and DB simultaneously; ensures consistency but adds write latency. **Write-behind (Write-back)** — writes to cache first, asynchronously flushes to DB; fastest writes but risk data loss. **Read-through** — cache itself fetches from DB on miss. **Cache invalidation** is the hardest problem: use **TTL-based expiry** (simple but may serve stale data), **event-driven invalidation** (publish cache-bust events on data changes), or **versioned keys**. Size your cache using the **80/20 rule** — 20% of data serves 80% of requests. Monitor **hit rate** (aim for >95%), **eviction rate**, and **memory usage**.

## 12. What is eventual consistency and when is it acceptable?

Eventual consistency means that if no new updates are made to a data item, eventually all reads will return the last updated value — but there's a window where different nodes may return different values. It's a weaker guarantee than strong consistency but enables **higher availability and lower latency** in distributed systems. It's acceptable for: **social media feeds** (seeing a post 2 seconds late is fine), **product catalogs** (price updates can propagate gradually), **analytics/counters** (approximate counts are okay), **search indexes** (slight lag in indexing), and **notification systems**. It's NOT acceptable for: **financial transactions** (account balances must be accurate), **inventory management** (overselling is costly), **authentication/authorization** (stale permissions are dangerous), and **booking systems** (double-booking is unacceptable). To work with eventual consistency: implement **read-your-writes** consistency (route reads to the same node that handled the write), use **conflict resolution** strategies (last-write-wins, vector clocks, CRDTs), and design UIs to be **optimistic** (show pending state, confirm later). Amazon's DynamoDB, Cassandra, and DNS are all eventually consistent systems. The key engineering decision is classifying each piece of data by its consistency requirement and applying the appropriate model.

## 13. How do message queues improve scalability?

Message queues (Kafka, RabbitMQ, SQS, NATS) **decouple producers from consumers**, allowing each to scale independently. Instead of Service A calling Service B synchronously (and waiting), A publishes a message to a queue, and B processes it when ready. This provides **temporal decoupling** (producer and consumer don't need to be online simultaneously), **load leveling** (queues absorb traffic spikes — producers can burst while consumers process at a steady rate), and **fan-out** (one message can be consumed by multiple services). For scalability: if order processing is slow, simply add more consumer instances — the queue distributes messages across them. **Kafka** excels at high-throughput event streaming with partitioned topics — each partition is consumed by one consumer in a group, enabling parallel processing. **RabbitMQ** is better for task queues with complex routing (exchanges, bindings). **SQS** is fully managed and auto-scales. Key patterns: **competing consumers** (multiple workers process from one queue), **pub/sub** (events broadcast to all subscribers), **dead letter queues** (capture failed messages for retry/debugging), and **exactly-once processing** (using idempotency keys). Queues also enable **saga patterns** for distributed transactions and **CQRS** where writes and reads are handled by separate services connected via events.

## 14. What is auto-scaling and how do you configure it properly?

Auto-scaling automatically adjusts the number of compute instances based on demand — adding instances during traffic spikes and removing them during lulls. In AWS, **Auto Scaling Groups (ASG)** manage EC2 instances with configurable min/max/desired counts. **Scaling policies**: **Target tracking** — set a target metric (e.g., keep CPU at 60%) and AWS adjusts instances automatically. **Step scaling** — define thresholds (CPU > 70% add 2 instances, > 90% add 5). **Scheduled scaling** — pre-scale for known traffic patterns (e.g., scale up at 8 AM). **Predictive scaling** — ML-based forecasting from historical patterns. Key metrics to scale on: **CPU utilization** (general compute), **request count per target** (for web servers), **queue depth** (for workers), **custom metrics** (business-specific like orders/min). **Cooldown periods** prevent thrashing — wait 300 seconds after scaling before evaluating again. For Kubernetes, **Horizontal Pod Autoscaler (HPA)** scales pods based on CPU/memory/custom metrics, and **Cluster Autoscaler** adds/removes nodes. **KEDA** (Kubernetes Event-Driven Autoscaling) scales based on external event sources like Kafka lag or SQS queue depth. Best practices: always set reasonable min (handle baseline traffic) and max (cost protection) limits, use **readiness probes** so new instances only receive traffic when ready, and pre-warm instances for predictable spikes.

## 15. How do you handle database connection pooling at scale?

Database connections are expensive — each PostgreSQL connection uses ~10MB of RAM, and most databases max out at a few thousand connections. With 50 app servers each opening 20 connections, you're at 1,000 connections. **Connection pooling** maintains a pool of reusable connections, drastically reducing the overhead. **Application-level pooling**: Libraries like HikariCP (Java), pgx (Go), or knex.js (Node.js) maintain a pool per app instance — set pool size = (number of CPU cores * 2) + number of spindles. **External pooler** like **PgBouncer** or **ProxySQL** sits between app servers and the database, multiplexing thousands of application connections into a smaller number of actual database connections. PgBouncer modes: **session** (connection assigned for entire client session), **transaction** (connection returned after each transaction — most efficient), **statement** (returned after each statement — restricts some features). At scale, PgBouncer in **transaction mode** can handle 10,000+ application connections with just 100 actual database connections. **AWS RDS Proxy** is a managed alternative that handles connection pooling, failover, and IAM authentication. Key settings to tune: `max_connections` on the database, `pool_size` per app instance, `idle_timeout` to reclaim unused connections, and `connection_lifetime` to refresh connections periodically. Monitor active vs. idle connections, wait times for acquiring a connection, and connection errors.

## 16. What is a microservices architecture and how does it enable scalability?

Microservices decompose a monolith into small, independently deployable services, each owning a specific business domain (user service, order service, payment service). Each service has its **own database** (database-per-service pattern), its **own deployment pipeline**, and can be written in **different languages/frameworks**. For scalability, this is transformative: you can scale **only the bottleneck service** — if search is under heavy load, scale search from 5 to 50 instances while keeping order service at 10 instances. Teams can **deploy independently** without coordinating releases, enabling faster iteration. Services communicate via **synchronous** (REST, gRPC) or **asynchronous** (message queues, event streaming) protocols. The **downsides** are significant: distributed transactions (solved via saga pattern), service discovery (Consul, Kubernetes DNS), inter-service latency, distributed tracing (Jaeger, Zipkin), and operational complexity (you're now managing 20+ deployments instead of 1). The **BFF pattern** (Backend for Frontend) creates specialized API gateways for web, mobile, etc. **API Gateway** handles cross-cutting concerns: authentication, rate limiting, request routing, and response aggregation. Conway's Law applies — team structure should mirror service boundaries. Start with a **modular monolith** and extract services only when you have clear scaling or team boundaries that justify the overhead.

## 17. Explain the circuit breaker pattern and why it's important for availability.

The circuit breaker pattern prevents cascading failures in distributed systems by wrapping calls to external services in a state machine with three states: **Closed** (normal operation — requests pass through, failures are counted), **Open** (circuit tripped — all requests immediately fail-fast without calling the downstream service, typically returning a fallback response), and **Half-Open** (after a timeout, a limited number of test requests are allowed through to check if the downstream service has recovered). When failures exceed a threshold (e.g., 50% failure rate over 10 seconds), the circuit opens. This is critical for availability because without it, a slow/failing downstream service causes **thread/connection pool exhaustion** in the calling service — threads pile up waiting for timeouts, and the caller itself becomes unresponsive, creating a **cascade**. Libraries: **Hystrix** (Netflix, now in maintenance), **Resilience4j** (Java), **Polly** (.NET), **opossum** (Node.js). In the codebase, our `server/gateway/circuitBreaker.ts` implements this pattern. Configure: **failure threshold** (5 failures to open), **timeout** (10 seconds in open state before half-open), **half-open request limit** (3 test requests). Combine with **retries** (with exponential backoff), **timeouts** (don't wait forever), **bulkheads** (isolate thread pools per dependency), and **fallbacks** (serve cached data, default responses, or degraded functionality).

## 18. How do you design for zero-downtime deployments?

Zero-downtime deployment ensures users experience no interruption during releases. **Blue-Green deployment**: maintain two identical environments (Blue=current, Green=new). Deploy to Green, test it, then switch the load balancer from Blue to Green. Instant rollback by switching back. Requires 2x infrastructure. **Rolling deployment**: gradually replace old instances with new ones — Kubernetes default. Set `maxSurge: 25%` and `maxUnavailable: 25%` to control the pace. Requires backward-compatible changes. **Canary deployment**: route a small percentage (1-5%) of traffic to the new version, monitor error rates and latency, then gradually increase. Automated canary analysis (Kayenta, Flagger) compares metrics between canary and baseline. **Database migrations** are the hardest part: use **expand-and-contract** — first deploy code that handles both old and new schemas, then migrate the schema, then remove old schema support. Never rename/drop columns in the same release as code changes. Use tools like **Flyway** or **Alembic** for versioned migrations. **Health checks** and **readiness probes** ensure new instances only receive traffic when fully initialized. **Graceful shutdown**: on SIGTERM, stop accepting new requests, finish in-flight requests (with a timeout), close connections, then exit. Feature flags (LaunchDarkly, Unleash) enable deploying code without activating features.

## 19. What is rate limiting and how do you implement it?

Rate limiting controls the number of requests a client can make in a given time window, protecting services from abuse, DDoS attacks, and resource exhaustion. **Token bucket algorithm**: a bucket holds N tokens, refilled at a constant rate. Each request consumes one token; if empty, request is rejected. Allows bursts up to bucket size. **Sliding window log**: stores timestamps of requests; counts requests in the window. Accurate but memory-intensive. **Sliding window counter**: approximates by weighting the previous window's count. Memory-efficient and accurate enough. **Fixed window counter**: simple but has boundary burst issues (2x limit at window edges). Implementation tiers: **API Gateway level** (Kong, AWS API Gateway) — first line of defense with per-API-key limits. **Application level** — more granular, business-logic-aware limits. **Use Redis** for distributed rate limiting — `INCR` + `EXPIRE` for fixed windows, or Redis Sorted Sets for sliding windows. Our codebase has `server/gateway/rateLimiter.ts` implementing this. HTTP responses: return **429 Too Many Requests** with `Retry-After` header and `X-RateLimit-Remaining`, `X-RateLimit-Limit`, `X-RateLimit-Reset` headers. Different limits per tier: authenticated users get 1000 req/min, anonymous get 100 req/min, premium get 10000 req/min. For distributed systems, consider **local + global** limiting: fast local check with periodic sync to a global counter.

## 20. How does consistent hashing help in distributed systems?

Consistent hashing is a technique for distributing data across nodes in a way that **minimizes redistribution when nodes are added or removed**. In regular hash-based distribution (`hash(key) % N`), changing N (adding/removing a server) remaps almost all keys. Consistent hashing maps both keys and nodes onto a **hash ring** (0 to 2^32). A key is assigned to the first node encountered clockwise on the ring. When a node is added, only keys between the new node and its predecessor move — approximately `K/N` keys (where K = total keys, N = total nodes) instead of nearly all keys. **Virtual nodes** solve uneven distribution: each physical node gets multiple positions on the ring (100-200 virtual nodes), ensuring even load distribution. Used in: **Amazon DynamoDB** (data partitioning), **Cassandra** (token ring), **Redis Cluster**, **CDN routing**, **Memcached** client-side sharding, and **load balancing** for WebSocket connections. For cache servers, consistent hashing is crucial: adding a cache node invalidates only ~1/N of cached data instead of everything (cache stampede). Implementation: use a sorted map of hash values to node IDs; for a key, find the next hash ≥ key's hash. Libraries: `hashring` (Node.js), Ketama algorithm. Monitor key distribution across nodes and adjust virtual node counts to achieve balance.

## 21. What is a distributed cache and how does Redis achieve high availability?

A distributed cache is a cache shared across multiple application instances, providing consistent cached data regardless of which server handles a request. **Redis** is the most popular choice, operating as an in-memory key-value store with sub-millisecond latency. **Redis Sentinel** provides HA for standalone Redis: Sentinel processes monitor the primary, detect failures via quorum voting, and automatically promote a replica to primary, updating clients. Requires minimum 3 Sentinel instances. **Redis Cluster** provides both HA and horizontal scaling: data is automatically sharded across multiple nodes using 16,384 hash slots. Each primary has replicas, and the cluster handles automatic failover. With 6 nodes (3 primaries + 3 replicas), you get both partitioning and redundancy. **Eviction policies**: `allkeys-lru` (evict least recently used — best general purpose), `volatile-ttl` (evict keys with nearest expiry), `noeviction` (return errors when full). For availability: enable **AOF (Append Only File) persistence** for durability, configure replicas with `min-replicas-to-write 1` to prevent data loss, and use **Redis Cluster** across availability zones. **AWS ElastiCache** provides managed Redis with Multi-AZ failover, automated backups, and cluster mode. Monitor: memory usage, hit rate, connected clients, evictions, and replication lag. Cache aside pattern + Redis + TTLs is the bread-and-butter caching strategy for most applications.

## 22. How do you design a multi-region architecture for global availability?

Multi-region architecture deploys your system across geographically distributed data centers to provide **low latency** (users hit the nearest region), **disaster recovery** (survive entire region failures), and **compliance** (data residency requirements). **Active-Passive**: one region handles all traffic, another is a warm standby. Simpler but wastes resources and has longer failover time (minutes). **Active-Active**: all regions serve traffic simultaneously. More complex but provides better latency and instant failover. Key challenges: **Data replication** — use database global tables (DynamoDB Global Tables, CockroachDB, Spanner) for multi-region writes with conflict resolution, or designate a primary region for writes with async replication to others. **DNS routing** — AWS Route 53 with latency-based or geolocation routing directs users to the nearest healthy region. **CDN** — serves static content from 200+ edge locations globally. **Session management** — use region-local Redis clusters with cross-region replication, or JWT tokens (stateless). **Deployment** — deploy to all regions simultaneously using a global CI/CD pipeline. **Consistency** — accept eventual consistency for most data, use strong consistency for critical operations by routing to a single primary. **Testing** — regularly run **game days** simulating region failures. Cost is 2-3x a single region, so justify it with business requirements for global availability and latency SLAs.

## 23. What is graceful degradation and how do you implement it?

Graceful degradation means a system continues to function (possibly with reduced capabilities) when components fail, rather than completely crashing. It's the opposite of a brittle system where one failure cascades to total outage. **Examples**: if the recommendation engine is down, show popular items instead of personalized ones. If the payment service is slow, queue orders for later processing. If search is unavailable, show category browsing. Implementation patterns: **Circuit breakers** detect downstream failures and serve fallback responses. **Timeouts** prevent waiting indefinitely — set aggressive timeouts (2-5 seconds) with fallbacks. **Feature flags** let you disable non-critical features under load (disable reviews, disable real-time tracking). **Bulkhead pattern** isolates resources per component — if search consumes all threads, order processing is unaffected (separate thread pools, separate process groups). **Priority queues** process critical operations (payments, orders) before non-critical ones (analytics, notifications) during overload. **Load shedding** rejects low-priority requests when the system is overwhelmed, preserving capacity for critical operations — return 503 with Retry-After. **Static fallbacks**: serve a cached version of the homepage if the backend is completely down. Design your UI to handle partial data — show loading spinners for failed sections rather than a full error page. Netflix's approach: every external call has a fallback, tested regularly via Chaos Engineering.

## 24. What is the CQRS pattern and how does it help with scalability?

**CQRS (Command Query Responsibility Segregation)** separates read and write operations into different models, potentially different databases. The **write side** handles commands (create, update, delete) with a normalized database optimized for consistency. The **read side** handles queries with denormalized views/projections optimized for fast reads. An **event/message** synchronizes the two sides — when a write occurs, an event is published that updates the read model. This enables **independent scaling**: reads are typically 10-100x more frequent than writes, so you can scale the read side massively with replicas, caching, and search indexes (Elasticsearch) while keeping the write side smaller. **Different storage per side**: writes to PostgreSQL (ACID transactions), reads from Redis (key lookups), Elasticsearch (full-text search), or pre-computed denormalized tables. Combined with **Event Sourcing**, CQRS stores all changes as an immutable event log, enabling audit trails, temporal queries, and rebuilding read models. **Downsides**: increased complexity, eventual consistency between read and write sides (read model may lag), more infrastructure to manage. **When to use**: high read/write ratio, complex query requirements, need for multiple read representations, or when read and write models differ significantly. **When to avoid**: simple CRUD apps, small teams, when strong consistency is required for every read.

## 25. How do you handle distributed transactions across microservices?

In microservices, each service has its own database, so traditional ACID transactions across services don't work. The **Saga pattern** is the standard solution. A saga is a sequence of local transactions where each step either succeeds (triggering the next step) or fails (triggering **compensating transactions** to undo previous steps). **Choreography-based saga**: services communicate via events — Order Service publishes "OrderCreated", Payment Service listens and processes payment, publishes "PaymentCompleted", Inventory Service listens and reserves stock. If payment fails, it publishes "PaymentFailed" and Order Service compensates by cancelling the order. Simple for 2-3 steps but becomes spaghetti with many services. **Orchestration-based saga**: a central **saga orchestrator** directs the sequence — "Step 1: charge payment, Step 2: reserve inventory, Step 3: assign delivery." If any step fails, the orchestrator runs compensation steps in reverse. Clearer flow but the orchestrator is a potential bottleneck. Our codebase has `server/microservices/saga/` implementing this. **Idempotency is critical** — compensating transactions or retries may execute multiple times, so every operation must be idempotent (use idempotency keys). **Transactional outbox pattern**: write events to an outbox table in the same local transaction as the data change, then a separate process publishes them — avoids the dual-write problem. Tools: **Temporal**, **AWS Step Functions**, or custom orchestrators.

## 26. What is back-pressure and how do you handle it in distributed systems?

Back-pressure is a mechanism where a system signals upstream components to slow down when it's overwhelmed, preventing overload and crash. Without back-pressure, a fast producer will overwhelm a slow consumer — buffers fill up, memory exhausts, and the system crashes. **Reactive Streams** (RxJava, Project Reactor, Node.js streams) have built-in back-pressure: the consumer requests N items, and the producer only sends N items. **Message queues** provide natural back-pressure: if consumers are slow, the queue grows, and producers can check queue depth before sending. In **Kafka**, consumer lag (difference between latest offset and consumer's offset) is the back-pressure signal — if lag grows, add more consumers. **HTTP-level back-pressure**: return **429 (Too Many Requests)** or **503 (Service Unavailable)** with `Retry-After` header when overwhelmed. **TCP-level**: TCP flow control naturally provides back-pressure via the receive window. **Load shedding**: when overloaded, drop low-priority requests to maintain service for high-priority ones. **Bounded queues/buffers**: use fixed-size buffers (e.g., Node.js highWaterMark on streams) — when full, the writer is paused. Implementation strategies: **rate limiting** at ingress, **circuit breakers** to stop calling overwhelmed services, **adaptive concurrency limits** (Netflix's concurrency-limits library) that dynamically adjust based on latency/error signals. Monitor queue depths, consumer lag, response times, and error rates to detect back-pressure needs.

## 27. How do you design an API for backward compatibility and versioning?

API backward compatibility is crucial — breaking changes cause client outages. **Versioning strategies**: **URL path versioning** (`/api/v1/users`, `/api/v2/users`) — most explicit and cacheable, but clutters URLs. **Header versioning** (`Accept: application/vnd.api+json;version=2`) — cleaner URLs but harder to test in browsers. **Query parameter** (`/api/users?version=2`) — simple but pollutes cache keys. **No versioning** (evolve in place) — use additive changes only. **Backward-compatible changes** (safe): adding new fields to responses, adding optional request parameters, adding new endpoints, adding new enum values (if clients handle unknown values). **Breaking changes** (dangerous): removing or renaming fields, changing field types, making optional fields required, changing response structure. **Strategy**: always make additive changes. When breaking changes are unavoidable, use **expand-and-contract**: introduce the new version alongside the old, migrate clients, then deprecate the old version with a sunset date. **GraphQL** avoids many versioning issues — clients request exactly the fields they need, and you can deprecate fields individually with `@deprecated`. For REST, use **content negotiation** and **feature flags**. Set deprecation timelines (6-12 months), monitor old version usage, and communicate changes via changelog and developer portal.

## 28. What is the bulkhead pattern and how does it prevent cascading failures?

The bulkhead pattern (named after ship compartments that prevent total flooding) **isolates components so a failure in one doesn't sink the entire system**. In software, this means allocating **separate resource pools** (thread pools, connection pools, process groups) for different functionalities or downstream dependencies. **Example**: your app calls three external services — Payment, Inventory, Notifications. Without bulkheads, all calls share one thread pool (say 200 threads). If Notifications becomes slow (10-second response), all 200 threads eventually block waiting for Notifications, and Payment/Inventory calls also start failing despite those services being healthy. **With bulkheads**: allocate 100 threads for Payment, 50 for Inventory, 30 for Notifications. When Notifications is slow, only its 30 threads are exhausted — Payment and Inventory continue normally. **Implementation levels**: **Thread pool isolation** (Hystrix/Resilience4j create separate pools per dependency), **Process isolation** (separate services in containers with resource limits — Kubernetes CPU/memory limits), **Infrastructure isolation** (separate database instances per service, separate Redis clusters for different use cases). **Kubernetes resource quotas** act as bulkheads — set CPU/memory limits per pod so one misbehaving service can't starve others. Combine with **circuit breakers** (stop calling failed services), **timeouts** (don't wait forever), and **queue-based load leveling** (buffer requests in queues).

## 29. What are the best practices for designing resilient APIs?

Resilient APIs handle failures gracefully and maintain service quality under adverse conditions. **1. Timeouts**: set explicit timeouts on every external call (HTTP, database, cache) — never wait indefinitely. Use aggressive timeouts (2-5 seconds) with fallbacks. **2. Retries with exponential backoff**: retry transient failures (network blips, 503s) with increasing delays (1s, 2s, 4s, 8s) plus jitter (random offset to prevent thundering herd). Cap retries at 3-5 attempts. **3. Circuit breakers**: stop calling failing services and serve fallbacks. **4. Idempotency**: design mutations to be safely retriable — use idempotency keys (`Idempotency-Key` header) to prevent duplicate processing. **5. Rate limiting**: protect services from abuse and overload. **6. Input validation**: validate all inputs at the API gateway level — reject malformed requests early. **7. Pagination**: always paginate list endpoints (cursor-based > offset-based) to prevent unbounded queries. **8. Health checks**: implement `/health` (readiness) and `/ready` (liveness) endpoints for load balancers and orchestrators. **9. Structured error responses**: return consistent error formats with error codes, messages, and correlation IDs for debugging. **10. Graceful shutdown**: handle SIGTERM by draining in-flight requests before stopping. Use **correlation IDs** (our `server/gateway/correlationId.ts`) to trace requests across services for debugging.

## 30. How does Kafka achieve high throughput and fault tolerance?

Kafka achieves **high throughput** through: **Sequential I/O** — writes are append-only to disk, achieving 600MB/s+ vs 100KB/s for random writes. **Zero-copy transfer** — data goes directly from disk to network socket via `sendfile()`, bypassing user-space copies. **Batching** — producers batch messages before sending, and brokers write in batches. **Compression** — messages are compressed (LZ4, Snappy, Zstd) in batches for efficient network transfer. **Partitioning** — topics are split into partitions distributed across brokers; each partition is a separate commit log enabling parallel reads/writes. A single Kafka cluster can handle millions of messages per second. **Fault tolerance** through: **Replication** — each partition is replicated across N brokers (replication factor, typically 3). One replica is the **leader** (handles reads/writes), others are **followers** (replicate from leader). **In-Sync Replicas (ISR)** — the set of replicas that are fully caught up. Producers can set `acks=all` to wait for all ISR to acknowledge — guarantees no data loss. If a leader fails, a follower from the ISR is elected as the new leader automatically. **Consumer groups** provide fault tolerance on the read side — if a consumer dies, its partitions are rebalanced to other consumers in the group. **Log retention** — messages are retained for a configurable period (7 days default) or size, enabling consumers to replay events. Kafka is the backbone for event-driven architectures, change data capture, and stream processing.

## 31. What is the sidecar pattern and how is it used in service meshes?

The sidecar pattern deploys a helper process alongside each application instance (in the same pod in Kubernetes) that handles **cross-cutting concerns**: networking, observability, security, and configuration. The application communicates with the sidecar over localhost, and the sidecar handles outbound/inbound traffic. In a **service mesh** (Istio, Linkerd), every service gets an **Envoy proxy sidecar** that intercepts all network traffic. Benefits: **Mutual TLS** — sidecars handle encryption between services without application code changes. **Load balancing** — client-side load balancing with advanced algorithms. **Circuit breaking and retries** — configured declaratively, not in application code. **Observability** — automatic metrics, distributed tracing, and access logs for every service-to-service call. **Traffic management** — canary deployments, A/B testing, traffic splitting, fault injection for chaos testing. The application code only knows about `http://localhost` calls — all the networking complexity is handled by the sidecar. **Downsides**: increased resource usage (each sidecar uses CPU/memory), added latency (~1-2ms per hop), operational complexity of managing the mesh, and debugging network issues becomes harder. **Istio** is the most popular service mesh with Envoy sidecars, providing mTLS, traffic policies, and observability. For smaller systems, a **library-based approach** (Resilience4j, express middleware) may be simpler than a full service mesh.

## 32. How do you implement health checks and why are they critical for availability?

Health checks are endpoints that report a service's operational status, enabling infrastructure to automatically detect and replace unhealthy instances. **Liveness check** (`/healthz`) — answers "is the process alive?" If it fails, the orchestrator restarts the container. Should check: process is running, not deadlocked, basic functionality works. Keep it lightweight (no external dependency checks) to avoid false positives. **Readiness check** (`/ready`) — answers "can this instance handle traffic?" Checks: database connections are established, cache is warm, dependent services are reachable. If it fails, the load balancer stops routing traffic to this instance but doesn't restart it. **Startup probe** (Kubernetes) — for slow-starting applications, prevents liveness checks from killing the container during initialization. **Deep health check** (`/health/detailed`) — checks all dependencies (DB, cache, queue, external APIs) with individual status. Used by monitoring dashboards, not load balancers (too slow, and an unhealthy dependency shouldn't make the instance unreachable). **Implementation**: return HTTP 200 for healthy, 503 for unhealthy, with a JSON body: `{"status": "healthy", "checks": {"database": "up", "redis": "up", "kafka": "degraded"}}`. Configure load balancer health checks with appropriate **interval** (10-30s), **timeout** (5s), **healthy threshold** (2 consecutive successes), and **unhealthy threshold** (3 consecutive failures). Health checks enable **auto-healing**: Kubernetes restarts failed pods, ASG replaces unhealthy EC2 instances, and load balancers route around failures — all automatically.

## 33. What is the strangler fig pattern for migrating from monolith to microservices?

The strangler fig pattern (named after a vine that gradually envelops and replaces a tree) **incrementally migrates** a monolith to microservices by routing specific functionality to new services while keeping the monolith running. Instead of a risky big-bang rewrite, you **extract one capability at a time**. **Step 1**: Place an **API gateway/proxy** in front of the monolith that routes all traffic to it initially. **Step 2**: Identify a bounded context to extract (e.g., user authentication). Build the new microservice alongside the monolith. **Step 3**: Update the API gateway to route `/auth/*` requests to the new service while everything else still goes to the monolith. **Step 4**: Verify the new service works correctly (shadow traffic, canary release). **Step 5**: Decommission the auth code in the monolith. **Step 6**: Repeat for the next bounded context. **Data migration** is the hardest part: the new service needs its own database. Use **change data capture** (Debezium) to sync data during the transition, then cut over. **Choose extraction order wisely**: start with modules that have the clearest boundaries, the most independent data, and the highest scaling needs. Avoid extracting tightly coupled modules first. The monolith might never fully disappear — and that's okay. Some core functionality may remain as a "macro-service." This pattern reduces risk dramatically compared to rewrites and provides value incrementally.

## 34. How do you monitor and observe distributed systems effectively?

The **three pillars of observability**: **Metrics** — numerical measurements over time (request rate, error rate, latency, CPU/memory usage). Use Prometheus for collection, Grafana for visualization. Key metrics: **RED** (Rate, Errors, Duration) for services, **USE** (Utilization, Saturation, Errors) for resources. **Logs** — structured event records. Use structured logging (JSON) with correlation IDs to trace requests across services. Centralize with ELK (Elasticsearch, Logstash, Kibana) or Loki. Log levels: ERROR (actionable failures), WARN (potential issues), INFO (business events), DEBUG (development only). **Traces** — end-to-end request paths through distributed services. Use OpenTelemetry for instrumentation, Jaeger or Zipkin for visualization. Each request gets a trace ID propagated through headers; each service adds a span with timing. **Alerting strategy**: alert on **symptoms, not causes** — alert on high error rate (symptom), not on high CPU (cause). Use **SLI/SLO/SLA** framework: define Service Level Indicators (latency p99 < 200ms), Service Level Objectives (99.9% of requests meet SLI), and error budgets (0.1% of requests can miss). Alert when you're burning through your error budget too fast. **Dashboards**: create **golden signal dashboards** per service (latency, traffic, errors, saturation) and a system-wide overview dashboard. **On-call practices**: runbooks for every alert, blameless post-mortems for incidents, and regular game days to test your monitoring.

## 35. What is the difference between horizontal and vertical partitioning of databases?

**Vertical partitioning** splits a table by columns — frequently accessed columns stay in the main table, rarely used or large columns (BLOBs, text) move to a separate table. Example: split a `users` table into `users_core` (id, name, email — hot data) and `users_profile` (bio, avatar, preferences — cold data). This improves query performance by reducing row size (more rows fit in memory/cache pages) and allows different storage optimizations per partition. It's essentially **normalization taken further**. **Horizontal partitioning (sharding)** splits a table by rows — different rows go to different tables or databases. Example: users 1-1M in partition 1, 1M-2M in partition 2 (range-based), or `hash(user_id) % 4` distributes across 4 partitions. This enables distributing data across multiple servers for scaling writes and storage. PostgreSQL supports **declarative partitioning** with range, list, or hash strategies natively. **Vertical partitioning** is simpler, done within a single database, and helps when some columns are accessed much more frequently than others. **Horizontal partitioning** is more complex but necessary when data volume exceeds a single server's capacity or when write throughput is the bottleneck. You can combine both: vertically partition first (separate hot/cold columns), then horizontally shard the hot table across multiple servers. Always measure query patterns before partitioning — premature partitioning adds complexity without benefit.

## 36. How does DNS-based load balancing work and what are its limitations?

DNS-based load balancing returns different IP addresses for the same domain name, distributing traffic across multiple servers or data centers. **Round Robin DNS**: returns IP addresses in rotating order. **Weighted DNS**: returns certain IPs more frequently based on server capacity. **Latency-based routing** (Route 53): resolves to the server with lowest latency for the user's location. **Geolocation routing**: returns IPs based on the user's geographic location for compliance or locality. **Health-checked DNS**: monitors backend health and removes unhealthy endpoints from DNS responses. **Failover routing**: primary endpoint gets all traffic; if it fails health checks, DNS switches to secondary. **Limitations**: **TTL caching** — DNS responses are cached by resolvers, ISPs, and clients for the TTL period (often 60-300 seconds). During this cache window, traffic still goes to failed servers. Lowering TTL helps but increases DNS query volume and some resolvers ignore low TTLs. **No real-time adaptation** — can't respond instantly to load changes. **Uneven distribution** — clients behind a NAT/proxy share one cached resolution, so a single IP might get disproportionate traffic. **Limited health visibility** — DNS only knows if a server is reachable, not if it's overloaded. DNS-based balancing is best used as a **first-level, global routing layer** (route to the nearest region) combined with **L4/L7 load balancers** at each region for precise, real-time traffic distribution.

## 37. What is the event-driven architecture and how does it improve scalability?

Event-driven architecture (EDA) structures communication around the production, detection, and consumption of **events** — significant state changes in the system. Instead of Service A calling Service B directly (request-response), Service A publishes an event ("OrderPlaced"), and any interested service subscribes and reacts independently. **Benefits for scalability**: **Loose coupling** — services don't know about each other, enabling independent deployment and scaling. **Asynchronous processing** — producers aren't blocked waiting for consumers; events are queued/streamed for processing at the consumer's pace. **Fan-out** — one event can trigger multiple consumers (order placed → update inventory AND send confirmation AND track analytics). **Event sourcing** — store all events as an immutable log; derive current state by replaying events. Enables audit trails, temporal queries, and rebuilding read models. **CQRS** pairs naturally with events for separate read/write optimization. **Technologies**: **Apache Kafka** (high-throughput streaming), **RabbitMQ** (message queuing with routing), **AWS EventBridge** (serverless event bus), **Redis Streams** (lightweight streaming). **Challenges**: eventual consistency (events take time to propagate), event ordering (use partition keys to maintain order within an entity), idempotency (consumers must handle duplicate events), debugging complexity (distributed event chains are hard to trace). **Event schema evolution**: use a schema registry (Confluent Schema Registry) with backward-compatible schema changes (Avro, Protobuf).

## 38. How do you design for fault tolerance in a cloud environment?

Fault tolerance means the system continues operating correctly even when components fail. **Design for failure** — assume every component will fail and plan for it. **Multi-AZ deployment**: spread instances across 2-3 availability zones (independent data centers with separate power/network). If one AZ goes down, others continue serving. **Auto-healing**: Kubernetes restarts crashed pods, ASG replaces failed EC2 instances. Use health checks to detect failures within seconds. **Data durability**: replicate databases across AZs (RDS Multi-AZ), use S3 (11 nines of durability) for object storage, and take regular automated backups. **Idempotent operations**: network issues cause retries; every operation must be safely retriable. **Retry with exponential backoff + jitter**: prevents thundering herd when a service recovers. **Circuit breakers**: stop calling failed dependencies and serve fallbacks. **Chaos engineering** (Netflix Chaos Monkey, Gremlin, LitmusChaos): intentionally inject failures in production to verify resilience — kill random pods, introduce network latency, simulate AZ failures. **Blast radius reduction**: deploy changes incrementally (canary), use feature flags, implement cell-based architecture (isolate failures to a subset of users). **Disaster recovery**: define RPO (Recovery Point Objective — max data loss tolerance) and RTO (Recovery Time Objective — max downtime tolerance). Test DR runbooks regularly — untested disaster recovery is not disaster recovery.

## 39. What is read-through vs write-through vs write-behind caching?

**Read-through cache**: the cache sits between the application and database. On a cache miss, the **cache itself** fetches from the database, stores it, and returns it. The application only talks to the cache. Pros: simple application code, consistent cache population. Cons: first request for each key is slow (cold start). Used by: Hibernate second-level cache, NCache. **Write-through cache**: every write goes to the cache AND database synchronously — the cache ensures both are updated before returning success. Pros: cache is always consistent with the database, reads are always fast (data is cached immediately). Cons: higher write latency (2 writes per operation), unnecessary caching of data that may never be read. **Write-behind (write-back) cache**: writes go to the cache first, then asynchronously flushed to the database in batches. Pros: very fast writes (application only waits for cache write), batching reduces database load. Cons: **risk of data loss** if the cache fails before flushing, complexity of managing the write queue. **Cache-aside (lazy loading)**: the application manages the cache explicitly — check cache, if miss fetch from DB and put in cache. Most common pattern. Pros: full control, only caches what's actually read. Cons: initial request penalty, potential for stale data. **Refresh-ahead**: proactively refreshes cached entries before they expire. Pros: always-fresh cache, no cold-start latency. Cons: wasted refreshes for data nobody reads.

## 40. How do you handle thundering herd problems?

The **thundering herd** occurs when a large number of processes/threads simultaneously compete for the same resource — typically when a popular cache entry expires and hundreds of concurrent requests all try to fetch from the database and repopulate the cache simultaneously. This can overwhelm the database and cause cascading failures. **Solutions**: **1. Cache locking (mutex)**: when a cache miss occurs, acquire a distributed lock (Redis `SET NX`). Only one request fetches from the database; others wait or serve stale data. **2. Request coalescing**: when multiple requests arrive for the same key during a cache miss, only one fetches from the database and all others wait for its result. Libraries: `singleflight` in Go, custom promise-based coalescing in Node.js. **3. Stale-while-revalidate**: serve the stale cached value immediately while asynchronously refreshing it. HTTP `Cache-Control: stale-while-revalidate=60`. **4. Probabilistic early expiration**: instead of all items expiring at exactly TTL, each request near expiration has a probability of triggering a refresh — `currentTime - (TTL * beta * log(random))`. Spreads refreshes over time. **5. Warm-up cache before TTL**: background process refreshes popular keys before they expire. **6. Circuit breaker on database**: if the DB is overwhelmed, trip the circuit and serve cached/default data. **7. Rate limiting on cache misses**: limit concurrent DB fetches for the same key. The combination of request coalescing + stale-while-revalidate is the most effective general solution.

## 41. What is a service registry and service discovery?

In a microservices architecture, services are dynamically scaled (instances are created/destroyed), so hard-coding IP addresses is impossible. **Service registry** is a database of available service instances and their network locations (IP:port). **Service discovery** is the mechanism by which services find each other. **Client-side discovery**: the client queries the service registry directly, gets a list of available instances, and load-balances across them (Netflix Eureka + Ribbon). Pros: client chooses the best instance, fewer network hops. Cons: discovery logic in every client, language-specific implementations. **Server-side discovery**: the client sends requests to a load balancer/router (e.g., AWS ALB, Kubernetes Service), which queries the registry and routes the request. Pros: simpler clients, language-agnostic. Cons: extra network hop, load balancer can be a bottleneck. **Kubernetes DNS** is the simplest form: `service-name.namespace.svc.cluster.local` resolves to the ClusterIP, and kube-proxy load-balances across healthy pods. **Consul** provides a full-featured registry with health checking, KV store, and DNS/HTTP interfaces. **etcd** and **ZooKeeper** are distributed KV stores used as registries. **Self-registration**: services register themselves on startup and deregister on shutdown. **Third-party registration**: a registrar (Kubernetes kubelet) monitors containers and updates the registry automatically. Our codebase has `server/microservices/registry/` implementing service discovery patterns.

## 42. How do you implement distributed tracing across microservices?

Distributed tracing tracks a request as it flows through multiple services, helping you understand latency, identify bottlenecks, and debug failures. **Core concepts**: a **trace** represents the entire request journey. Each service operation creates a **span** with start time, duration, tags, and logs. Spans have parent-child relationships forming a **trace tree**. A **trace ID** (unique per request) and **span ID** are propagated via HTTP headers (`traceparent`, `X-B3-TraceId`). **OpenTelemetry** is the industry-standard instrumentation framework — it provides SDKs for all major languages to automatically instrument HTTP clients, database drivers, and message queues. Instrumented code: `const span = tracer.startSpan('processOrder'); span.setAttribute('order.id', orderId); ... span.end()`. **Backend systems**: **Jaeger** (CNCF, open source, battle-tested at Uber), **Zipkin** (Twitter origin), **AWS X-Ray** (managed), **Grafana Tempo** (works with Grafana). **Sampling strategies**: not every request needs tracing in production — use **probabilistic sampling** (trace 1% of requests), **rate-limited sampling** (10 traces/sec), or **tail-based sampling** (always capture slow/error traces). **Correlation**: connect traces to logs (include trace ID in log entries) and metrics (exemplars link metrics to specific traces). Combine with our `server/gateway/correlationId.ts` middleware that generates and propagates correlation IDs. Traces reveal: which service is slowest, where errors originate, N+1 query patterns, and unnecessary sequential calls that could be parallelized.

## 43. What is data replication lag and how do you handle it?

Replication lag is the delay between a write on the primary database and that write becoming available on replicas. In async replication (PostgreSQL streaming replication, MySQL binlog replication), lag is typically milliseconds but can grow to seconds or minutes during heavy write loads, network issues, or replica maintenance. **Problems caused by lag**: A user updates their profile (write to primary), then immediately views their profile (read from replica) — they see the old data (read-your-writes violation). A user sees item A in a list (newer data) then on the detail page sees old data for item A (non-monotonic reads). **Solutions**: **1. Read-your-writes consistency**: after a user writes, route their subsequent reads to the primary for a short window (e.g., 5 seconds). Use a cookie/session flag to track recent writes. **2. Monotonic reads**: pin a user session to a specific replica (session affinity), so they always read from the same replica. **3. Synchronous replication**: one replica is synchronous (waits for confirmation), others async. Guarantees at least one replica is current but adds write latency. **4. Monitor lag**: `pg_stat_replication` in PostgreSQL, `SHOW SLAVE STATUS` in MySQL. Alert if lag exceeds threshold (e.g., > 5 seconds). **5. Causal consistency**: version your data and let clients specify "read at least version X." **6. Accept eventual consistency**: for non-critical reads (dashboards, search results), stale data is acceptable. Always design your application knowing that replicas may be behind.

## 44. How does Kubernetes enable scalability and high availability?

Kubernetes (K8s) is a container orchestration platform that automates deployment, scaling, and management of containerized applications. **Scalability**: **Horizontal Pod Autoscaler (HPA)** automatically scales pods based on CPU, memory, or custom metrics (requests/sec, queue depth). **Vertical Pod Autoscaler (VPA)** adjusts CPU/memory requests per pod. **Cluster Autoscaler** adds/removes worker nodes when pods can't be scheduled due to resource constraints. **KEDA** enables event-driven scaling (scale to zero, scale based on Kafka consumer lag). **High Availability**: **ReplicaSets** ensure a specified number of pod replicas are always running — if a pod dies, K8s creates a new one automatically. **Pod Disruption Budgets (PDB)** ensure minimum available pods during voluntary disruptions (node maintenance, rolling updates). **Anti-affinity rules** spread pods across nodes/AZs to survive hardware failures. **Rolling updates** with configurable `maxSurge`/`maxUnavailable` enable zero-downtime deployments. **Liveness probes** restart stuck containers, **readiness probes** remove unready pods from service endpoints. **Service mesh** (Istio) adds circuit breaking, retries, and mTLS. **Multi-AZ clusters** with nodes in different availability zones survive AZ failures. **Control plane HA**: managed Kubernetes (EKS, GKE) provides a highly available control plane across multiple AZs. Kubernetes also enables **resource isolation** with namespaces, resource quotas, and limit ranges, preventing one team's workload from starving another's.

## 45. What is the difference between optimistic and pessimistic locking for concurrent access?

**Pessimistic locking** assumes conflicts are likely and prevents them by locking the resource before any modification. When a transaction reads a row, it acquires a lock (`SELECT ... FOR UPDATE`), blocking other transactions from modifying or even reading (depending on lock mode) until the lock is released. Pros: guarantees no conflicts, simple to reason about. Cons: reduces concurrency (blocked transactions wait), risk of **deadlocks** (two transactions lock resources in opposite order), poor for high-concurrency or long-running transactions. **Optimistic locking** assumes conflicts are rare and detects them at write time. Each row has a **version number** or **timestamp**. On read, the application notes the version. On write, it checks: `UPDATE ... SET version = version + 1 WHERE id = X AND version = old_version`. If the row was modified by another transaction (version changed), the update affects 0 rows, and the application retries or reports a conflict. Pros: no locks held, maximum concurrency, no deadlocks. Cons: retries under high contention waste work, requires application logic to handle conflicts. **When to use each**: Pessimistic for high-contention scenarios (booking the last seat, updating account balances), short transactions, and critical sections. Optimistic for low-contention scenarios (editing user profiles, updating product descriptions), web applications where read-modify-write cycles are common, and distributed systems where distributed locks are expensive. Most ORMs (Hibernate, Prisma, Sequelize) support both patterns.

## 46. How do you handle hot partitions/hot keys in distributed databases?

A **hot partition** occurs when disproportionate traffic hits a single partition/shard in a distributed database, creating a bottleneck while other partitions sit idle. Example: a viral product's key on a single DynamoDB partition, or a celebrity's user_id on a single Cassandra node. **Detection**: monitor per-partition metrics — uneven request distribution, throttling on specific partitions, high latency on specific keys. DynamoDB shows throttled requests per partition; Cassandra has `nodetool tablehistograms`. **Solutions**: **1. Key design/salting**: add a random suffix to hot keys (`product:123:0`, `product:123:1`, ... `product:123:9`). Reads query all suffixed keys and aggregate. Spreads load across 10 partitions instead of 1. **2. Caching**: put a cache (Redis, DAX for DynamoDB) in front of hot keys — most reads hit cache, not the database. **3. Write sharding**: for counters, maintain N sub-counters and sum on read. Instead of incrementing `likes:post123`, increment `likes:post123:shard{random(0,10)}` and sum all shards for reads. **4. Time-based partitioning**: avoid using timestamp as the sole partition key (all current writes hit the latest partition). Add another dimension like `region + timestamp`. **5. DynamoDB adaptive capacity**: automatically redistributes throughput to hot partitions (but has limits). **6. Application-level fan-out**: for extreme hot keys (millions of reads/sec), implement an in-memory cache with short TTL in your application tier. **Prevention**: always analyze access patterns before choosing partition keys; avoid sequential IDs, timestamps, or high-cardinality values as sole partition keys.

## 47. What is chaos engineering and how do you practice it?

Chaos engineering is the discipline of **intentionally injecting failures into production systems** to build confidence in the system's ability to withstand turbulent conditions. Netflix pioneered it with Chaos Monkey (randomly kills production instances). **Principles**: 1. Start with a **hypothesis** ("Our system maintains <200ms p99 latency when one database replica fails"). 2. **Define steady state** — normal metrics (error rate, latency, throughput). 3. **Introduce failures** — kill instances, inject network latency, fill disks, corrupt DNS. 4. **Observe** — compare metrics during chaos vs steady state. 5. **Learn and fix** — discovered weaknesses become improvements. **Types of experiments**: **Infrastructure**: kill VMs/pods, simulate AZ failure, exhaust CPU/memory. **Network**: add latency (100-500ms), drop packets (5-20%), partition networks between services. **Application**: slow down dependencies, return errors from external APIs, corrupt data. **Tools**: **Chaos Monkey** (Netflix, kills instances), **Gremlin** (commercial, comprehensive failure injection), **LitmusChaos** (Kubernetes-native, CNCF), **AWS Fault Injection Simulator** (managed chaos for AWS resources), **Toxiproxy** (simulate network conditions). **Best practices**: start small (non-production, then low-traffic periods), automate experiments to run regularly, have a **kill switch** to stop experiments instantly, always have observability in place first, and run **game days** where the team practices incident response. Chaos engineering has evolved from "breaking things" to a rigorous engineering practice that continuously validates system resilience.

## 48. How do you implement a distributed rate limiter across multiple servers?

A distributed rate limiter enforces request limits consistently across all application instances, preventing clients from exceeding limits by hitting different servers. **Redis-based fixed window**: use `INCR` and `EXPIRE` atomically — `MULTI; INCR rate:{client}:{window}; EXPIRE rate:{client}:{window} 60; EXEC`. If the count exceeds the limit, reject. Simple but has boundary burst issues (client can send 2x limit at the window boundary). **Redis-based sliding window log**: store each request timestamp in a sorted set — `ZADD rate:{client} {now} {uuid}; ZREMRANGEBYSCORE rate:{client} 0 {now-window}; ZCARD rate:{client}`. Accurate but memory-intensive for high-limit endpoints. **Token bucket with Redis**: store `{tokens, last_refill_time}` in Redis. On each request: calculate tokens to add since last refill, subtract one, update atomically using Lua scripts for atomicity. Allows controlled bursts. **Sliding window counter** (best balance): approximate the current window's count by weighting the previous window — `count = prev_window_count * (1 - elapsed/window_size) + current_window_count`. Accurate enough, memory-efficient. **Lua scripts** in Redis ensure atomicity without race conditions. **Local + global hybrid**: each instance maintains a local counter (fast, no network call) and periodically syncs with Redis global counter. Provides better performance but slightly less accurate. **Considerations**: handle Redis failures gracefully (fail open — allow requests — or fail closed — deny requests, depending on security requirements). Use consistent client identification (API key > IP address, because NATs share IPs).

## 49. What are SLIs, SLOs, SLAs, and error budgets?

**SLI (Service Level Indicator)** is a quantitative measure of a service's behavior — the metric you actually measure. Examples: request latency p99, error rate (% of 5xx responses), availability (% of successful health checks), throughput (requests/sec). Choose SLIs from the **user's perspective** — "99% of API requests complete in under 200ms" matters more than "CPU stays under 70%." **SLO (Service Level Objective)** is the target value for an SLI — the goal you commit to internally. Example: "99.9% of requests return successfully (availability SLO)" or "p99 latency < 200ms for 99.5% of time windows." SLOs should be **ambitious but achievable** — don't set 99.99% if your architecture only supports 99.9%. **SLA (Service Level Agreement)** is a contractual commitment to customers with consequences (refunds, credits) for violations. SLAs should be **less aggressive than SLOs** — if your SLO is 99.9%, your SLA might be 99.5%, giving you a buffer. **Error budget** = 1 - SLO. If your SLO is 99.9%, your error budget is 0.1% (43.8 minutes/month). The error budget is "permission to fail" — use it for deployments, experiments, and maintenance. **Error budget policy**: when the budget is exhausted, freeze feature deployments and focus on reliability. When budget is healthy, ship features faster. This creates a **data-driven balance** between innovation velocity and reliability. Google's SRE book popularized this framework. Track error budget burn rate — if you've consumed 50% of your monthly budget in the first week, slow down.

## 50. How do you design a system for 99.99% availability (four nines)?

99.99% availability means **≤ 52.6 minutes of downtime per year** — approximately 4.4 minutes per month. This is extremely demanding and requires meticulous engineering across every layer. **Architecture**: multi-AZ deployment (minimum 3 AZs), no single points of failure anywhere. Every component (load balancer, app server, database, cache, queue) must be redundant. **Database**: multi-AZ primary with synchronous replication to at least one standby, automatic failover (RDS Multi-AZ, Aurora), regular backup testing. **Deployments**: zero-downtime deployments using blue-green or rolling updates. Canary releases detect issues before full rollout. Automated rollback if error rates spike. **Monitoring**: sub-minute detection of issues through health checks, real-time metrics, and alerting. Automated remediation for common failures (instance replacement, pod restart). On-call rotation with < 5 minute response time. **Dependencies**: every external call has timeouts, retries, circuit breakers, and fallbacks. Graceful degradation for non-critical features. Cache data aggressively to survive database outages. **Testing**: regular chaos engineering experiments, quarterly disaster recovery drills, load testing to 3x expected peak. **Change management**: strict change control process, feature flags for all new features, infrastructure as code with peer review. **Operational**: error budget tracking, blameless post-mortems for every incident, SLO dashboards visible to all engineers. **Trade-offs**: four nines costs significantly more than three nines — more infrastructure, more engineering time, slower feature velocity. Calculate the business cost of downtime to justify the investment. Most consumer applications target 99.9%; financial and healthcare systems may need 99.99%+.
